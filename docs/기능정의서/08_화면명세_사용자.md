## USER-1 · 프로필

**목적** 본인의 프로필 정보를 조회하고 수정한다.
**사용자** 슈퍼관리자, 관리자 / [2차] 임대인, 임차인
**진입 경로** 사이드바 아래 계정 영역 → 프로필

### 【입출력 항목】

```
프로필사진, 이름, 회사이름(위탁관리 회사 등 소속이 있는 경우),
이메일, 연락처, 비밀번호 변경
```

### 【동작 규칙】

- 이메일은 로그인 아이디로 사용되므로 수정 시 재인증을 거친다
- 비밀번호 변경은 현재 비밀번호 확인 후 진행한다
- [2차] 임대인·임차인도 포털 오픈 시 동일 화면을 사용한다

### 【설계 의도】

- 이메일 수정을 허용하되 재인증을 요구한다. 확인 없이 변경하면 계정 접근이 불가능해진다

### 【연관 화면】 USER-2
### 【알림】 없음

---

## USER-2 · 사용자 조회

**목적** 전체 사용자를 조회하고 계정 상태를 관리한다.
**사용자** 슈퍼관리자
**진입 경로** 설정 메뉴 → 사용자 관리

### 【입출력 항목】

```
필터: 사용자역할(슈퍼관리자/관리자/임대인/임차인), 계정상태(정상/차단됨), 담당건물

[목록]
이름, 회사이름, 역할, 담당건물, 이메일, 연락처, 마지막로그인시점, 계정상태,
더보기(상세보기, 비밀번호 재설정 메일 발송, 접근차단 / 차단해제)
```

### 【동작 규칙】

- 사용자 역할은 슈퍼관리자·관리자·임대인·임차인 4종이다
- 소속 운영사의 사용자만 조회한다. 타 운영사 사용자는 표시하지 않는다
- **담당건물**은 관리자에게만 표시한다. 슈퍼관리자는 `전체`로 표시한다
- 상단에 `새로운 사용자 등록` 버튼을 배치한다. **등록 가능한 역할은 관리자뿐이다.** 슈퍼관리자는 운영사당 1명이며 SYS-2에서만 발급한다 → USER-3
- 임대인 계정은 PRO-2, 임차인 담당자 계정은 CTR-2에서 자동 생성된다. 본 화면에서는 조회와 수정만 수행한다
- **계정은 삭제하지 않는다. 접근 차단(비활성화)만 지원한다**
- 차단된 계정은 로그인할 수 없으며 목록에 `차단됨`으로 표시된다
- **비밀번호는 관리자가 직접 지정하지 않는다.** `비밀번호 재설정 메일 발송`을 실행하면 본인이 링크를 통해 설정한다
- [2차] 임대인·임차인은 포털 오픈 후 로그인 가능하다. 그때까지 목록에 `포털 미오픈`으로 표시해 로그인 불가 사유를 안내한다

### 【설계 의도】

- 계정 삭제를 금지하는 이유는 이력과 원장에 처리자로 기록된 계정이 소멸하면 추적이 불가능해지기 때문이다 → 3.6
- 관리자가 타인의 비밀번호를 인지하는 상태를 만들지 않는다

### 【연관 화면】 USER-1, USER-3, PRO-2, CTR-2
### 【알림】 이메일 — 비밀번호 재설정 메일

## USER-3 · 사용자 등록

**목적** 신규 관리자 계정을 등록한다.
**사용자** 슈퍼관리자
**진입 경로** USER-2 → `새로운 사용자 등록`

### 【입출력 항목】

```
이름, 회사이름(소속이 있는 경우), 연락처, 이메일,
사용자역할(관리자 — 고정),
담당건물(복수 선택)
```

### 【동작 규칙】

- **등록 가능한 역할은 관리자뿐이다.** 슈퍼관리자는 운영사당 1명이며 SYS-2에서만 발급한다 → 3.7
  임대인은 PRO-2, 임차인 담당자는 CTR-2에서 생성된다. 임차인은 계약이, 임대인은 건물이 존재해야 성립하는 개념이므로 계정만 별도로 생성하지 않는다
- 저장 시 입력한 이메일로 **초대 메일**을 발송한다. 메일에는 로그인 링크가 포함되며 사용자가 직접 비밀번호를 설정한다
- **시스템이 임시 비밀번호를 생성해 메일에 기재하지 않는다**
- 이메일 주소는 로그인 아이디로 사용한다
- **담당건물은 슈퍼관리자만 배정한다.** 관리자는 배정된 건물의 데이터만 조회·수정할 수 있다 → 3.7
- 담당건물을 지정하지 않은 관리자는 조회 가능한 건물이 없다. 목록은 빈 상태로 표시한다
- 담당건물 변경은 즉시 반영하며 변경 내역을 이력에 기록한다
- **건물 등록·상세(PRO-2·3)의 건물관리자는 여기서 등록한 관리자 중에서 고른다.** 건물관리자로 고르면 그 건물이 담당건물로 배정된다(같은 기록). 한 건물에 여러 관리자, 한 관리자에 여러 건물이 가능하다
- [2차] 역할 정의와 기능별 권한 부여는 권한 관리(USER-4·5)와 함께 구현한다

### 【설계 의도】

- 계정 생성 경로를 단일화해 동일 인물의 중복 계정 발생을 방지한다
- 담당 건물을 계정 등록 시점에 함께 지정해 별도 배정 화면을 두지 않는다. 건물 수가 증가하면 전용 화면을 검토한다
- 메일 본문에 비밀번호를 평문으로 기재하지 않는다. 메일함이 노출되면 그대로 유출되며, 임차인 계정은 계약·청구 정보에 접근한다

### 【연관 화면】 USER-2, PRO-2, CTR-2
### 【알림】 이메일 — 계정 등록 시 초대 메일

## USER-6 · 임차인 조회

**목적** 전체 임차인(법인·개인사업자)을 조회한다.
**사용자** 슈퍼관리자, 관리자
**진입 경로** 메인 메뉴 → 임차인 관리

### 【입출력 항목】

```
필터: 건물고유이름, 계약상태(디폴트: 진행중),
      사업자구분(법인/개인사업자), 미납 여부

[목록]
상호(법인명), 사업자구분, 사업자등록번호, 대표자명,
임차 유닛(건물고유이름 + 유닛고유번호. 복수 시 묶어서 표시),
대표 담당자(이름, 연락처, 이메일),
미납액,
[2차] 임차인 포털 초대 상태(초대하지않음 / 초대완료),
더보기(상세보기)
```

### 【동작 규칙】

- 임차인은 법인 또는 개인사업자이며 **사업자등록번호로 식별한다** → 2.3
- **목록은 사업자 단위로 한 행씩 표시한다.** 한 사업자가 여러 유닛·여러 건물을 임차하는 경우가 빈번하므로 유닛 단위로 나열하면 동일 회사가 반복된다. 임차 유닛은 한 칸에 묶어 표시한다
- 미납액은 해당 사업자의 모든 계약을 합산한 금액이다
- 상호 또는 상세 보기 클릭 시 개별 임차인 조회로 이동한다 → USER-7
- **사업자등록번호는 유일값이다.** 계약 등록 시 기존 사업자를 조회해 표시하고 없을 때만 신규 등록한다 → CTR-2
- [2차] 포털 초대 상태는 포털 오픈 후 의미가 발생한다. 그때까지 표시만 하고 초대 기능은 동작하지 않는다

### 【설계 의도】

- 유닛 단위로 나열하면 동일 회사가 반복되어 해당 회사와의 전체 거래 규모를 파악할 수 없다
- 사업자 중복 등록 시 미납 합계와 계약 이력이 분리된다

### 【연관 화면】 USER-7, CTR-2, PAY-13
### 【알림】 없음

## USER-7 · 개별 임차인 조회

**목적** 개별 임차인(사업자) 정보를 조회하고 수정한다. 계약 이력과 거래 요약을 확인한다.
**사용자** 슈퍼관리자, 관리자
**진입 경로** USER-6 행 클릭 / CTR-3 요약 탭 계약정보의 임차인 이름
**화면 구성** 요약 · 계약이력 · 자료보관 — **3개 탭**

### 【입출력 항목】

```
(제목) - 수정 가능. 사업자등록번호는 수정 불가
상호(법인명), 사업자구분(법인/개인사업자), 사업자등록번호

───── 요약탭 ─────
(사업자 정보) - 수정 가능
상호(법인명), 대표자명, 사업장주소, 업태·종목,
입금자명 별칭(복수. 추가/삭제),
청구서 합쳐 보내기(예/아니오, 디폴트: 아니오)  ※ 같은 건물 계약이 여럿일 때만 의미가 있다 → PAY-1

(대표 담당자)  ※ 읽기 전용. 계약 화면에서 수정
담당자명, 직위, 연락처, 이메일

(거래 요약)
누적 청구액, 누적 수납액, 현재 미납액, 보증금 잔액, 최근 입금일

───── 계약이력탭 ─────
[목록]
계약고유이름, 건물고유이름, 유닛고유번호, 계약기간,
임대료, 고정관리비, 보증금, 계약상태
→ 클릭 시 계약 상세로 이동

───── 자료보관 탭 ─────
건물 자료보관(PRO-3)과 같은 목록 · 상세 · 삭제 · 업로드 패널. 귀속 대상은 이 사람으로 정해져 있고, 카테고리는 귀속 대상에 맞는 것만 → 3.1

───── [2차] 요청탭 ─────  REQ 계열과 함께 구현
```

### 【동작 규칙】

**수정 위치 구분**
- **사업자 정보**(상호, 대표자명, 사업장주소, 업태·종목)는 본 화면에서 수정하며 **해당 사업자의 모든 계약에 공통 반영**된다
- **담당자 정보**는 계약마다 다를 수 있으므로 계약 상세에서 수정한다 → CTR-3. 본 화면에는 대표 담당자만 읽기 전용으로 표시한다
- **사업자등록번호는 수정할 수 없다.** 사업자를 식별하는 값이므로 변경 시 계약과 거래 기록의 연결이 단절된다. 오입력 시 계약을 다시 등록한다

**거래 요약**
- 해당 사업자의 **모든 계약을 합산한 값**이다
- 계약 원장(CTR-3)은 계약 단위이므로 여러 계약을 보유한 사업자의 합계는 본 화면에서만 확인할 수 있다

**계약이력**
- 해당 사업자의 모든 계약을 과거부터 현재까지 표시한다. 계약을 추가·수정하지 않으며 조회만 수행한다

**기타**
- 주민등록번호는 수집하지 않는다. 개인사업자도 사업자등록번호로 식별한다

### 【설계 의도】

- 사업자 정보와 담당자 정보의 수정 위치를 분리한다. 같은 회사라도 건물·유닛에 따라 담당자가 다르다
- 계약 단위 원장만으로는 다계약 사업자의 합계를 확인할 수 없어 거래 요약을 별도로 제공한다

### 【연관 화면】 USER-6, CTR-3, PAY-6
### 【알림】 없음

## USER-8 · 임대인 조회

**목적** 전체 임대인(건물주)을 조회한다.
**사용자** 슈퍼관리자, 관리자
**진입 경로** 메인 메뉴 → 임대인 관리

### 【입출력 항목】

```
필터: 건물고유이름, 임대인구분(개인/법인/개인사업자),
      위탁운영계약 상태(진행중/만료임박/만료)

[목록]
임대인명, 임대인구분, 상호(법인명), 사업자등록번호,
보유 건물(건물고유이름 + 보유지분(%). 복수 시 묶어서 표시),
연락처, 이메일,
위탁운영계약 남은 일수(건물별. 가장 임박한 건물을 우선 표시),
더보기(상세보기, 보고서 뽑기)
```

### 【동작 규칙】

- 임대인은 개인·법인·개인사업자로 구분한다. 상업용 건물주는 법인인 경우가 많다
- **임대료 세금계산서가 임대인 명의로 발행되므로 사업자등록번호를 필수로 보관한다**
- **사업자등록번호는 유일값이다.** 건물 추가 등록 시 기존 임대인을 조회해 표시하고 없을 때만 신규 등록한다 → PRO-2
- **목록은 임대인 단위로 한 행씩 표시한다.** 한 임대인이 여러 건물을 보유하는 경우가 많으므로 보유 건물과 지분을 한 칸에 묶어 표시한다
- 공동소유 건물은 보유지분(%)을 함께 표시한다
- **위탁운영계약은 건물 단위다.** 필터의 위탁운영계약 상태는 보유 건물 중 하나라도 해당하면 조회된다
- 위탁운영계약 만료 시 해당 건물의 관리 권한이 소멸하므로, 만료 90일 전부터 목록과 대시보드에 표시한다 → DASH-1
- `보고서 뽑기` 실행 시 해당 임대인의 월간 보고서로 이동한다 → REP-1

### 【설계 의도】

- 임대인을 개인으로만 취급하면 세금계산서 발행 명의 정보를 보관할 곳이 없다

### 【연관 화면】 USER-9, PRO-2, REP-1, DASH-1
### 【알림】 없음

## USER-9 · 개별 임대인 조회

**목적** 개별 임대인 정보를 조회하고 수정한다. 보유 건물과 위탁운영계약을 관리한다.
**사용자** 슈퍼관리자, 관리자
**진입 경로** USER-8 행 클릭
**화면 구성** 요약 · 건물 · 자료보관 — **3개 탭**

### 【입출력 항목】

```
(제목) - 수정 가능. 사업자등록번호는 수정 불가
임대인명, 임대인구분(개인/법인/개인사업자), 상호(법인명), 사업자등록번호

───── 요약탭 ─────
(기본정보) - 수정 가능
대표자명, 주소(사업장주소), 연락처, 이메일

───── 건물탭 ─────
[목록]
건물고유이름, 건물주소, 건물유형, 보유지분(%), 유닛 수, 공실률,
위탁운영계약(기간, 남은 일수)    ※ 조회 전용. 수수료 · 운영방식은 대외비라 보이지 않는다
더보기(건물정보 → PRO-3 요약탭, 유닛정보 → PRO-3 유닛탭, 보고서 → REP-1)

───── 자료보관 탭 ─────
건물 자료보관(PRO-3)과 같은 목록 · 상세 · 삭제 · 업로드 패널. 귀속 대상은 이 사람으로 정해져 있고, 카테고리는 귀속 대상에 맞는 것만 → 3.1

───── [2차] 요청탭 ─────  REQ 계열과 함께 구현
```

### 【동작 규칙】

**수정**
- 임대인 정보(상호, 대표자명, 사업장주소, 연락처, 이메일)는 본 화면에서 수정하며 **해당 임대인의 모든 건물에 공통 반영**된다
- **사업자등록번호는 수정할 수 없다.** 세금계산서 발행 명의이자 임대인 식별자다

**위탁 운영 방식**
- 운영 방식은 두 가지가 존재한다

| 방식 | 내용 | 범위 |
|---|---|---|
| 임대인 직수취 | 임대료·관리비가 임대인 통장으로 입금되고, 임대인이 위탁 운영사에 수수료를 지급한다. 임대료·관리비 납부 계좌(PRO-2)가 곧 임대인 계좌다 | **1차** |
| 위탁사 수취 후 정산 | 위탁 운영사 통장으로 수취한 뒤 수수료를 제외하고 임대인에게 송금한다 | [2차] |

- 운영 방식은 건물 단위로 지정한다
- **초기 오픈은 임대인 직수취 방식을 전제한다**
- 관리 수수료는 1차에 기록하지 않는다(대외비). 수수료 청구와 수납 처리는 2차에서 다룬다

**위탁운영계약**
- **건물 단위로 관리한다.** 본 화면의 건물탭에는 건물별 위탁운영계약을 조회 전용으로 표시하며, 수정은 건물 상세 요약탭에서 수행한다 → PRO-3
- 만료 90일 전부터 대시보드에 표시한다
- [2차] 임대인이 위탁운영계약서를 직접 열람하는 화면(OWN-2)은 임대인 포털과 함께 구현한다

**건물탭**
- 해당 임대인이 보유한 모든 건물을 지분·유닛 수·공실률과 함께 표시한다. 건물을 추가·수정하지 않으며 조회와 이동만 수행한다
- 임대인 계정은 PRO-2에서 생성된다. 본 화면에서 신규 생성하지 않는다 → 3.7

### 【설계 의도】

- 위탁운영계약을 임대인이 아닌 건물에 둔다. 계약서를 건물마다 별도로 작성하므로 임대인 단위로 두면 건물별 만료일을 관리할 수 없다
- 위탁운영계약 만료는 계약 만료와 동일한 구조로 사전 고지한다. 만료 시 관리 권한 자체가 소멸하기 때문이다

### 【연관 화면】 USER-8, PRO-2, PRO-3, REP-1, DASH-1
### 【알림】 없음 / 내부 — 위탁운영계약 만료 임박 안내

## SYS-1 · 운영사 조회

**목적** 시스템에 등록된 전체 운영사를 조회한다.
**사용자** 시스템 운영자
**진입 경로** 시스템 관리 메뉴

### 【입출력 항목】

```
필터: 운영사구분(실운영/검증용), 상태(정상/중지)

[목록]
운영사명, 운영사구분, 사업자등록번호, 슈퍼관리자명, 건물수, 계약수,
등록일, 상태, 더보기(상세보기, 중지 / 중지해제)

[상단] 새로운 운영사 등록
```

### 【동작 규칙】

- **시스템 운영자만 접근한다.** 슈퍼관리자·관리자에게는 메뉴를 노출하지 않는다
- **운영사구분이 `검증용`인 행은 실운영과 다른 배경색으로 표시한다** → 11장 7.2.4
- 운영사는 삭제하지 않는다. 중지만 지원한다. 중지된 운영사의 사용자는 로그인할 수 없다
- 건물수·계약수는 규모 확인용 집계다
- [2차] 요금제·사용량 통계는 외부 운영사 수임 시점에 추가한다

### 【설계 의도】

- 운영사 목록을 업무 화면과 분리해 일상 운영 중 노출되지 않게 한다
- 검증용 운영사를 시각적으로 구분해 실 데이터 오염을 방지한다

### 【연관 화면】 SYS-2
### 【알림】 없음

## SYS-2 · 운영사 등록·수정

**목적** 운영사를 생성하고 슈퍼관리자 계정을 발급한다.
**사용자** 시스템 운영자
**진입 경로** SYS-1 → `새로운 운영사 등록` 또는 행 클릭

### 【입출력 항목】

```
(운영사 정보)
운영사명, 운영사구분(실운영 / 검증용), 사업자등록번호, 대표자명,
주소, 연락처, 로고

(슈퍼관리자)  신규 등록 시 1명 필수
슈퍼관리자명, 이메일, 연락처

(운영 설정)
구글 계정 로그인 사용 여부
```

### 【동작 규칙】

- 저장 시 슈퍼관리자 이메일로 **초대 메일**을 발송한다. 본인이 비밀번호를 설정한다 → 3.7
- **운영사구분은 등록 후 변경할 수 없다.** 검증용 데이터가 실운영으로 전환되는 것을 차단한다
- 운영사명과 로고는 해당 운영사의 화면 상단과 발송 문서에 표시한다
- 구글 계정 로그인은 운영사 단위로 설정한다. 사용하지 않는 운영사는 이메일 로그인만 가능하다 → 11장 7.4.1
- 슈퍼관리자 교체는 시스템 운영자가 SYS-2에서 한다
- [2차] 요금제·계약 기간·청구 정보는 외부 운영사 수임 시점에 추가한다

### 【설계 의도】

- 운영사 생성을 단일 화면으로 제한해 데이터가 소속 없이 생성되는 상황을 방지한다
- 운영사구분을 변경 불가로 두어 검증 데이터와 실 데이터의 경계를 유지한다

### 【연관 화면】 SYS-1, USER-2, USER-3
### 【알림】 이메일 — 슈퍼관리자 초대 메일
