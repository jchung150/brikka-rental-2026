# 6. 데이터 요구사항

본 장은 시스템이 저장해야 할 대상(엔터티)과 속성, 관계를 정의한다.
**스키마 설계의 입력물이며 스키마 자체가 아니다.** 컬럼 타입·인덱스·테이블 분할은 스키마 설계에서 결정한다.

---

## 6.1 설계 원칙

| # | 원칙 | 내용 |
|---|---|---|
| 1 | **원장이 원본이다** | 잔액·수납액·미납액·납부상태는 원장 거래에서 산출하는 파생값이다. 성능을 위해 별도 보관하더라도 원장과 불일치 시 원장이 기준이다 |
| 2 | **기록은 수정·삭제하지 않는다** | 원장 거래·이력·검침 기록·발송 내역은 추가만 허용한다. 오류는 취소 거래 또는 조정 기록으로 정정한다 |
| 3 | **식별자는 유일해야 한다** | 임차인·임대인은 사업자등록번호로 식별한다. 동일 사업자의 중복 등록을 허용하지 않는다 |
| 4 | **마감된 기간은 잠긴다** | 마감된 건물 × 월에는 원장 거래를 추가할 수 없다 |
| 5 | **기존 골격을 유지한다** | 건물 → 유닛 → 계약 → 청구 → 수납 구조는 인수 스키마를 계승한다 |

| 엔터티 | 사유 |
|---|---|
| 계약 차량 | 차량번호 미관리. 주차면을 계약에 직접 배정 |

| 거래 행 | 거래일시 · 거래구분 · 입금자명(원문·정규화) · 입금액 · 매칭 결과(자동/후보/미매칭) · 매칭 계약 · 승인 여부 · 생성된 입금 |

거래 행은 입금액이 0보다 큰 행만 보관한다.
