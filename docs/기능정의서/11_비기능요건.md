# 7. 비기능 요건

본 장은 화면 명세에 담기지 않는 요건을 정의한다. 보안·권한·가용성·성능·운영이 대상이다.
각 요건에는 근거를 함께 기재한다. 개발자가 제약의 이유를 알아야 대안을 판단할 수 있다.

요건은 충족 여부를 판정할 수 있는 형태로 기술한다. "보안을 강화한다"와 같이
검증이 불가능한 표현은 사용하지 않는다.

---

## 7.1 원칙

| # | 원칙 | 적용 |
|---|---|---|
| 1 | **최소 권한** | 업무 수행에 필요한 범위만 부여한다. 되돌릴 수 없는 행위는 상위 권한으로 제한한다 |
| 2 | **기록 불변** | 원장 거래·이력·로그는 추가만 허용한다. 응용 프로그램 계정에 삭제 권한을 부여하지 않는다 |
| 3 | **경계 강제** | 운영사 간 데이터 격리는 응용 프로그램이 아니라 데이터베이스가 강제한다 |
| 4 | **검증된 구성요소 우선** | 인증·암호화·파일 접근 제어는 직접 구현하지 않고 검증된 서비스를 사용한다 |

원칙 4의 근거: 인증·암호화·파일 접근 제어는 직접 구현 시 결함이 발생하기 쉬운 영역이며,
결함의 영향이 전체 데이터에 미친다. 검증된 서비스를 사용한다 → 7.11.

---

## 7.2 다중 운영사 구조

### 7.2.1 범위

본 시스템은 **하나의 시스템 위에서 복수의 운영사가 각자의 건물을 관리하는 구조**로 설계한다.

```
시스템 운영자 (테온하우스)
  ├ 운영사 A  → 건물 → 유닛 → 계약
  ├ 운영사 B  → 건물 → 유닛 → 계약
  └ 운영사 C  → 건물 → 유닛 → 계약
```

1차 개발에서 **운영사 3개를 실제로 운용한다.** 1개는 실 데이터, 2개는 검증용 가상 데이터를
사용한다. 따라서 운영사 격리는 설계상의 대비가 아니라 **1차에서 동작해야 하는 기능**이다.

### 7.2.2 격리 요건

| # | 요건 | 근거 |
|---|---|---|
| 1 | 모든 업무 데이터는 소속 운영사를 식별하는 값을 보유한다 | 이후 구조 변경 없이 격리를 적용하기 위함 |
| 2 | **격리는 데이터베이스 수준에서 강제한다** (Row Level Security 등) | 조회 조건을 응용 프로그램이 일일이 부여하면 누락이 발생한다. 한 곳의 누락이 곧 타 운영사 데이터 노출이다 |
| 3 | 첨부파일은 운영사별로 분리된 경로에 저장한다 | 파일 단위 접근 제어와 향후 분리를 가능하게 한다 |
| 4 | 운영사마다 달라질 수 있는 값을 코드에 고정하지 않는다 | 청구항목·연체율·건물 기본값·회사명·로고가 해당한다 |
| 5 | 인증을 특정 조직의 계정 체계에 종속시키지 않는다 | 외부 운영사는 해당 조직의 계정을 보유하지 않는다 |
| 6 | 사용자 역할을 2종으로 고정하지 않는다 | 운영사 경계를 넘는 역할이 존재한다 → 7.3 |

### 7.2.3 1차 범위에서 제외

다음은 1차 범위가 아니다. 구현하지 않는다.

가입 절차 / 요금제 및 과금 / 운영사별 화면 테마 / 운영사 단위 사용량 통계

운영사 생성은 시스템 운영자가 SYS-2에서 직접 수행한다. 자동 가입 절차는 두 번째 외부
운영사를 수임하는 시점에 검토한다.

### 7.2.4 운영사 전환

시스템 운영자는 복수 운영사를 조회할 수 있다. 재로그인 없이 화면에서 전환한다.

| 요건 | 내용 |
|---|---|
| 현재 운영사 표시 | 모든 화면 상단에 상시 노출한다 |
| 검증용 운영사 구분 | 실 운영사와 **다른 배경색**으로 표시한다 |
| 전환 기록 | 전환 시각과 대상 운영사를 보안 로그에 남긴다 → 7.7 |

배경색 구분의 근거: 검증용 운영사에서 작업 중임을 인지하지 못한 상태의 입력은
실 데이터 오염으로 이어진다. 화면상 구분이 유일한 방어 수단이다.

## 7.3 사용자와 권한

### 7.3.1 역할 — 3종

| 역할 | 소속 | 범위 | 1차 |
|---|---|---|---|
| **시스템 운영자** | 테온하우스 | 전체 운영사 | SYS-1·2 화면만 제공 |
| **슈퍼관리자** | 각 운영사 1명 | 소속 운영사 전체 | 구현 |
| **관리자** | 각 운영사 복수 | **배정된 건물** | 구현 |

시스템 운영자는 운영사 생성과 슈퍼관리자 계정 발급을 담당한다. 업무 화면은 사용하지 않는다.

### 7.3.2 권한 구분

**되돌릴 수 없거나 운영사 전체에 영향을 주는 행위**만 슈퍼관리자로 제한한다.
그 외는 동등하게 부여한다.

| 슈퍼관리자 전용 | 슈퍼관리자 · 관리자 공통 |
|---|---|
| 건물 등록 · 삭제 | 유닛 등록 · 수정 |
| 계약 삭제 | 계약 등록 · 수정 · 해지 |
| **계약의 임대료 · 고정관리비 수정 · 인상 예약** | 정산액 대납 계약 지정 |
| **월 마감 취소** | 월 마감 |
| **건물별 관리비 설정** | — |
| 사용자 등록 · 권한 변경 · 차단 | 청구서 발행 · 취소, 청구 정정(감액 · 추가 청구) |
| 관리자별 담당 건물 배정 | 수납 등록 · 배분 · 입금 무효, 환불, 오납 표시 · 환불 기록 |
| 유닛 `비운영중` 지정 · 해제 | 검침 입력 · 조정, 정산 확정 |
| | 문서 등록 · 삭제, 엑셀 내보내기 |

제한의 근거는 신뢰가 아니라 실수 방지다. 월 마감을 취소하면 해당 월의 모든 금액이
재계산 대상이 되므로 단독 수행을 허용하지 않는다.

### 7.3.3 담당 건물 배정

| 요건 | 내용 |
|---|---|
| 배정 주체 | 슈퍼관리자. USER-3에서 복수 건물을 선택한다 |
| 적용 범위 | 건물·유닛·계약·청구·수납·정산·문서의 **모든 조회와 수정** |
| 미배정 관리자 | 조회 가능한 건물이 없다. 목록은 빈 상태로 표시한다 |
| 슈퍼관리자 | 배정과 무관하게 소속 운영사 전체를 조회한다 |
| 배정 변경 | 즉시 반영한다. 변경 내역은 이력에 기록한다 |

### 7.3.4 검사 위치

권한 검사는 **서버에서 매 요청 수행한다.** 화면에서 메뉴나 버튼을 숨기는 것은
권한 검사가 아니다. 숨겨진 기능도 직접 호출이 가능하다.

## 7.4 인증

### 7.4.1 로그인

| 항목 | 요건 |
|---|---|
| 기본 방식 | 이메일 + 비밀번호 + **TOTP** (인증 앱 6자리) |
| 추가 방식 | 구글 계정 로그인. 운영사 단위로 사용 여부를 설정한다 |
| TOTP 적용 | **관리자 이상 전원 필수.** 최초 로그인 시 등록을 강제한다 |
| 계정 식별자 | 이메일 주소 |

구글 로그인을 기본으로 삼지 않는 근거: 외부 운영사는 특정 조직의 계정 체계를 보유하지
않는다. 조직 계정 보유 운영사만 선택적으로 사용한다.

### 7.4.2 비밀번호

| 항목 | 요건 | 근거 |
|---|---|---|
| 최소 길이 | 12자 | |
| 복잡도 | 문자 종류 조합을 강제하지 않는다 | TOTP 적용 시 복잡도보다 길이가 유효하다. 조합 강제는 예측 가능한 패턴을 유발한다 |
| 유출 이력 검사 | 기존 유출 목록에 포함된 비밀번호는 거부한다 | 대입 공격의 주 경로다 |
| 초기 비밀번호 | **발급하지 않는다.** 초대 링크를 통해 본인이 설정한다 | 고정 초기값은 미변경 상태로 잔존한다 |

### 7.4.3 세션

| 항목 | 값 |
|---|---|
| 유지 시간 | 8시간 |
| 유휴 시간 초과 | 2시간 무조작 시 재인증 |
| 로그아웃 | 세션 즉시 무효화 |

### 7.4.4 계정 잠금

5회 연속 실패 시 15분간 잠근다. 잠금 해제 후에도 실패가 반복되면 슈퍼관리자가 해제한다.
잠금 발생은 보안 로그에 기록한다.

### 7.4.5 계정 생성과 차단

| 대상 | 생성 | 비고 |
|---|---|---|
| 슈퍼관리자 | 시스템 운영자가 발급 (SYS-2) | 운영사당 1명 |
| 관리자 | 슈퍼관리자가 초대 (USER-3) | 초대 메일 → 본인이 비밀번호 설정 |
| 임차인 담당자 · 임대인 | 계약·건물 등록 시 생성 | [2차] 로그인 기능 개시 시 초대 메일 발송 |

**퇴사자 계정은 삭제하지 않고 차단한다.** 작업 이력의 수행자 정보를 보존해야 한다.
차단 즉시 기존 세션을 무효화한다.

## 7.5 접근 제어

### 7.5.1 접속 경로

관리자는 사무실과 자택에서 접속한다. 출발지 IP 제한은 적용하지 않는다.
따라서 로그인 화면이 공개된 상태이며 다음으로 방어한다.

| 수단 | 내용 |
|---|---|
| WAF | 웹 공격 차단. OWASP 규칙 집합 적용 |
| 봇 차단 | 로그인 화면에 자동화 도구 차단을 적용한다 (Cloudflare Turnstile) |
| 계정 잠금 | 7.4.4 |
| TOTP | 비밀번호 유출만으로는 접근이 불가하다 |

### 7.5.2 첨부파일

| 요건 | 내용 |
|---|---|
| 접근 조건 | **권한 확인 후에만 발급한다.** 파일 주소만으로 접근되어서는 안 된다 |
| 링크 유효 시간 | 10분 |
| 내려받기 기록 | 계약서·사업자등록증·신분증·건물서류 카테고리 문서는 수행자·시각을 기록한다 |
| 일괄 내려받기 상한 | 1회 50건 / 500MB (DOC-1) |
| 저장 경로 | 운영사별 분리 → 7.2.2 |

### 7.5.3 통신

전 구간 HTTPS를 적용한다. HTTP 접속은 HTTPS로 전환한다.

## 7.6 데이터 보호

### 7.6.1 수집하지 않는 정보

**주민등록번호를 수집하지 않는다.** 임차인은 사업자이며 계약 주체는 법인 또는 개인사업자다
(→ 3.1). 담당자 개인의 주민등록번호도 수집 대상이 아니다.

개발 시 주민등록번호 저장·암호화·파기 절차를 고려할 필요가 없다.

### 7.6.2 보호 대상과 취급

| 대상 | 취급 |
|---|---|
| 임대료·관리비 납부 계좌 · 환불계좌 | 목록 화면은 **뒤 4자리만 표시**한다. 상세 화면에서 전체를 표시한다 |
| 은행 거래내역 업로드 파일 | 업로드 **90일 경과 후 자동 삭제**한다. 매칭 결과는 원장에 영구 보존되므로 원본 보관이 불필요하다 |
| 임차인 담당자 정보 | 계약 종료 **5년 경과 후 마스킹**한다 → 7.6.3 |
| 임차인 상호 · 사업자등록번호 | 마스킹하지 않는다. 거래 기록의 식별자다 |

### 7.6.3 마스킹

보존 기간이 경과한 담당자 정보는 **원본을 마스킹 값으로 덮어쓴다.**
화면 표시만 가리는 방식은 적용하지 않는다. 원본이 잔존하면 보호 효과가 없다.

| 항목 | 변환 후 |
|---|---|
| 담당자명 | `홍*동` |
| 연락처 | `010-****-5678` |
| 이메일 | `h***@company.co.kr` |

금액·거래 기록은 변환하지 않는다.

### 7.6.4 데이터 반출

엑셀·PDF 내보내기는 **데이터가 시스템 외부로 이동하는 유일한 경로**다.
단일 파일에 전체 임차인의 상호·연락처·계약 금액·미납액이 포함된다.

| 요건 | 내용 |
|---|---|
| 권한 | 관리자 이상. 담당 건물 범위 내로 한정한다 |
| 기록 | 수행자·시각·대상·건수를 보안 로그에 기록한다 → 7.7 |

차단이 아니라 기록으로 통제하는 근거: 엑셀 반출을 차단하면 실무가 성립하지 않는다.
기록이 남는다는 사실 자체가 억제 수단이다.

## 7.7 기록과 보관

### 7.7.1 두 종류의 기록

| 구분 | 내용 | 조회자 |
|---|---|---|
| **업무 이력** (→ 3.6) | 계약·금액·상태의 변경 | 관리자, [2차] 임대인 |
| **보안 로그** (본 절) | 인증·권한·반출 | 시스템 운영자 |

### 7.7.2 보안 로그 대상

로그인 성공 · 로그인 실패 · 계정 잠금 · 권한 변경 · 담당 건물 배정 변경 ·
계정 차단 및 해제 · **계약서 등 민감 문서 내려받기** · **엑셀·PDF 내보내기** ·
월 마감 취소 · 운영사 전환

각 항목에 수행자·시각·출발지 IP·대상을 기록한다.

### 7.7.3 보관 기간

| 대상 | 기간 | 근거 |
|---|---|---|
| 원장 거래 · 청구 · 수납 | **영구** | 계약 기간 2년, 분쟁은 퇴거 정산 시점에 발생한다. 증빙 보존 의무 5년 |
| 업무 이력 | **영구** | 텍스트 기록이며 용량 부담이 없다 |
| 보안 로그 | **1년** | 임대 업무는 연 단위로 순환한다. 전년 동월과의 대조가 가능해야 한다 |
| 은행 거래내역 원본 | 90일 | → 7.6.2 |

### 7.7.4 삭제 방지

| 요건 | 내용 |
|---|---|
| 응용 프로그램 계정 권한 | 원장 거래·이력·로그 테이블에 **DELETE·UPDATE 권한을 부여하지 않는다** |
| 정정 방법 | 취소 거래 또는 조정 기록을 추가한다 (→ 3.6, 6.1) |

데이터베이스 권한으로 강제하는 근거: 응용 프로그램의 결함으로도 기록이 삭제되지 않아야 한다.

## 7.8 가용성

### 7.8.1 복구 목표

| 지표 | 목표 | 의미 |
|---|---|---|
| 데이터 유실 허용 범위 | **24시간** | 장애 시 최대 1일분의 입력을 재수행한다 |
| 복구 소요 시간 | **4시간** | 장애 인지부터 서비스 재개까지 |

24시간을 허용하는 근거: 검침값과 고지서는 원본 서류가 존재하므로 재입력이 가능하다.
재수행 부담이 가장 큰 작업은 은행 거래내역 매칭이며, 1일분은 감당 가능한 범위다.

### 7.8.2 백업

| 요건 | 내용 |
|---|---|
| 주기 | 1일 1회 이상. 시점 복구(PITR)를 지원하는 구성을 사용한다 |
| 보관 | 7일 이상 |
| **복구 시험** | **반기 1회 실제 복구를 수행하고 결과를 기록한다** |
| 첨부파일 | 데이터베이스와 동일 주기로 백업한다 |

복구 시험을 요건에 포함하는 근거: 시험하지 않은 백업은 장애 시점에 실패한다.

### 7.8.3 장애 대응

유지보수 계약으로 대응 체계를 확보한다. 대응 시간·연락 체계·책임 범위는
**유지보수 계약서에서 정한다.** 본 문서는 복구 목표만 정의한다.

## 7.9 성능

### 7.9.1 규모 전제

| 항목 | 현재 | 3년 후 |
|---|---|---|
| 운영사 | 3 (검증용 2 포함) | 10 내외 |
| 건물 | 5 | 30 |
| 유닛 | 100 | 600 |
| 관리자 | 5 | 20 내외 |
| 월 청구서 | 100건 | 600건 |
| 월 원장 거래 | 약 1,000건 | 약 6,000건 |
| 5년 누적 원장 거래 | — | 30만 건 이하 |

이 규모에서는 일반적인 관계형 데이터베이스 구성으로 충분하다.
성능 최적화보다 **정확성과 격리**를 우선한다.

### 7.9.2 응답 목표

| 대상 | 목표 |
|---|---|
| 목록 조회 (100건 기준) | 2초 이내 |
| 상세 조회 | 2초 이내 |
| 청구서 일괄 발행 (600건) | 5분 이내. 진행 상태를 화면에 표시한다 |
| 관리비 안분 계산 (건물 1개) | 10초 이내 |
| 엑셀 내보내기 (1,000행) | 10초 이내 |

일괄 처리는 **중단 시 재개가 가능해야 한다.** 600건 중 300건에서 실패한 경우
이미 처리된 건을 중복 발행하지 않는다.

### 7.9.3 인덱스

조회 조건과 정렬 기준으로 사용하는 항목에 인덱스를 부여한다
(→ 6장 무결성). 운영사 식별값은 모든 조회의 선행 조건이므로 인덱스 구성에 반영한다.

## 7.10 운영

### 7.10.1 환경 분리

| 환경 | 용도 | 데이터 |
|---|---|---|
| 개발 | 기능 개발 | 임의 생성 데이터 |
| 운영 | 실 업무 | 실 데이터 + 검증용 운영사 2개 |

**운영 데이터를 개발 환경으로 복사하지 않는다.** 검증은 운영 환경 내 검증용 운영사에서
수행한다(→ 7.2.1). 검증용 운영사의 데이터는 임의로 생성하며 **실 임차인 정보를
복제하지 않는다.**

### 7.10.2 개발자의 운영 데이터 접근

| 항목 | 내용 |
|---|---|
| 접근 | 허용한다. 장애 원인 분석에 필요하다 |
| 전제 조건 | **유지보수 계약에 비밀유지 조항을 포함한다** |
| 기록 | 접근 경로와 시점을 확인할 수 있도록 구성한다 |

### 7.10.3 비밀 정보 관리

| 요건 | 내용 |
|---|---|
| 저장 위치 | 배포 환경의 설정으로만 관리한다. 소스 코드에 포함하지 않는다 |
| 담당자 변경 시 | **모든 키·토큰·비밀번호를 재발급한다** |
| 대상 | 데이터베이스 접속 정보, 인증 키, 파일 저장소 키, 메일 발송 토큰 |

설정 예시 파일에는 실제 값을 기재하지 않는다. 형식만 표기한다.

### 7.10.4 의존성 관리

| 요건 | 내용 |
|---|---|
| 취약점 점검 | 사용 중인 라이브러리의 알려진 취약점을 정기 점검한다 |
| 긴급 대응 | 고위험 등급 취약점은 계약 범위와 무관하게 즉시 대응한다 |
| 정기 업데이트 | 유지보수 계약 범위에서 수행한다 |

## 7.11 인프라 구성

### 7.11.1 선정 결과

| 영역 | 선정 | 근거 |
|---|---|---|
| 데이터베이스 | **Supabase (PostgreSQL) · 서울 리전** | 인증·파일 저장·백업·격리(RLS) 기능을 포함한다. 국내 리전을 제공하여 국외 이전 문제가 발생하지 않는다 |
| 인증 | Supabase Auth | TOTP·초대 메일·비밀번호 재설정·계정 잠금을 직접 구현하지 않는다 → 7.1 원칙 4 |
| 파일 저장 | Supabase Storage | 권한 기반 접근 제어를 포함한다 |
| DNS · WAF · 봇 차단 | **Cloudflare** | 기 사용 중 |
| 도메인 | **brikka.co.kr** | |

리전은 프로젝트 생성 시점에 확정된다. 이후 변경은 전체 데이터 이전을 수반한다.
**서울 리전으로 생성한다.**

### 7.11.2 메일 발송

| 항목 | 내용 |
|---|---|
| 발신 주소 | `billing@brikka.co.kr` |
| **도메인 인증** | **SPF · DKIM · DMARC를 설정한다** |
| 발송 형태 | 청구 내역서는 **PDF 첨부**로 발송한다 → 7.11.3 |
| 발송 실패 | 관리자 화면에 표시한다. 자동 재시도는 1회로 제한하고 이후 수동 재발송한다 |
| 발송 이력 | 대상·시각·결과를 기록한다 (NTF-6) |

도메인 인증을 요건으로 명시하는 근거: 미설정 시 청구서가 수신자의 스팸함으로 분류된다.
수신 실패는 미납 처리와 미납 안내로 이어져 분쟁을 유발한다.

### 7.11.3 청구서 발송 방식

청구 내역서는 **PDF 파일을 메일에 첨부**하여 발송한다. 열람 링크 방식을 사용하지 않는다.

| 방식 | 판정 |
|---|---|
| PDF 첨부 | **채택.** 1차에는 임차인 포털이 없으므로 링크 방식은 인증 없는 공개 열람이 된다 |
| 열람 링크 | [2차] 임차인 포털 개시 후 전환을 검토한다 |
