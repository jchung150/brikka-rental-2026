2. 주요 결정 사항

2.1 원장 중심 구조

금액과 상태를 직접 수정하는 방식에서 거래를 기록하고 상태를 산출하는 방식으로 전환했습니다. 수납·취소·환불이 모두 거래로 남으므로 금액 변동 경로를 추적할 수 있습니다.

표 4. 구조 전환의 내용
구분기존 방식확정 방식
금액 정정기록을 수정취소 거래를 추가. 기록은 삭제하지 않음
납부상태담당자가 지정거래의 결과로 산출. 직접 수정 불가
장부 확정없음월 마감 신설. 건물 × 월 단위로 잠금

* 월 마감 취소는 슈퍼관리자 권한으로 제한하고 사유 입력을 필수화했습니다.

2.2 다중 운영사 구조

하나의 시스템에서 복수의 운영사가 각자의 건물을 관리하는 구조로 설계했습니다. 1차 운용 단계에서 운영사 3개를 실제로 운영합니다. 1개는 실 데이터, 2개는 검증용 가상 데이터를 사용합니다.

표 5. 1차 구현 범위와 제외 범위
1차 구현2차 이관
운영사 단위 데이터 격리 (데이터베이스 수준 강제)가입 절차
운영사 조회·등록 화면 2개요금제 및 과금
역할 3종 — 시스템 운영자 / 슈퍼관리자 / 관리자운영사별 사용량 통계
관리자별 담당 건물 배정운영사별 화면 테마
검토 의견

검증용 운영사 2개를 두면 실제 임차인 데이터를 건드리지 않고 청구·마감·해지를 시험할 수 있습니다. 데이터 격리의 결함도 외부 운영사를 수임하기 전에 발견됩니다.

구조를 나중에 추가하려면 전체 테이블을 변경해야 하므로, 1차에 확보하는 편이 총비용이 낮습니다.

2.4 신규 개발로 확정

기존 시스템의 코드를 계승하지 않고 신규 개발로 진행합니다.

표 7. 판단 근거
#근거
11차 범위의 핵심인 청구·수납·원장·정산이 기존 코드에 존재하지 않음. 기존 구현은 건물·유닛·계약의 등록과 조회까지
2원장 중심 구조와 다중 운영사 구조가 기존 구조와 양립하지 않음
3재사용 가능 범위를 산정한 결과 3~5일 분량. 화면 구성요소 51종은 공개 표준 모음이며 재설치가 가능

* 운영 중인 데이터가 없어 데이터 이관 작업이 발생하지 않습니다. 개발사 견적에서 해당 항목이 제외됩니다.

4. 다음 단계

표 10. 착수 순서
#단계내용
1화면 목업주요 화면을 실제 형태로 제작. 배치·항목 수·조작 흐름 검증
2명세 보정목업에서 도출된 변경을 기능정의서에 반영
3스키마 설계6부 데이터 요구사항을 기준으로 테이블 설계
4개발사 선정기능정의서 및 목업 제시. 견적 비교
5개발 착수
목업을 스키마보다 먼저 두는 이유

화면은 업무의 형태이고 데이터 구조는 이를 담는 그릇입니다. 순서가 바뀌면 화면을 데이터 구조에 맞추게 됩니다.

목업 단계의 수정 비용은 사실상 없으나, 스키마는 확정 후 변경 시 이미 작성된 코드의 수정을 수반합니다. 변경 비용이 낮은 단계에서 문제를 찾습니다.

목업은 전체 35개 화면이 아니라 복잡도가 높거나 판단이 필요한 10~15개를 대상으로 합니다. 목록 형태가 반복되는 화면은 대표 화면 1개로 갈음합니다.

5. 리스크 및 대응

표 11. 리스크
리스크대응
목업 단계에서 명세 변경 발생변경을 전제로 한 절차. 변경분을 기능정의서에 반영한 뒤 스키마 설계에 착수
다중 운영사 채택에 따른 1차 범위 증가화면 2개와 격리 구조로 한정. 가입·요금제·통계는 2차 이관
개인정보 관련 법률 검토 미완임차인 담당자 정보 수집에 따른 처리방침 필요 여부 확인. 오픈 전 완료
청구서 메일의 스팸 분류발신 도메인 인증 설정. 발송량을 단계적으로 증가시켜 평판 확보
개발사 미선정목업 완료 시점에 접촉 착수. 기능정의서와 목업을 동시 제시
종합 의견

요건 정의 단계를 완료했습니다. 착수 전 결정이 필요한 항목은 남아 있지 않습니다.

다음 2주는 화면 목업에 사용합니다. 이 단계에서 발견되는 문제는 개발 착수 후 발견될 경우와 비교해 수정 비용이 현저히 낮습니다.
