‣ 구조 결정 4건 세부내용

1. 원장 중심 구조

  • 금액·상태를 직접 수정하는 방식에서 거래를 기록하고 상태를 산출하는 방식으로 전환
  • 금액 정정: 기록 수정 → 취소 거래 추가. 기록은 삭제하지 않음
  • 납부상태: 담당자 지정 → 거래의 결과로 산출. 직접 수정 불가
  • 거래유형 8종 — 청구 / 청구취소 / 수납 / 수납취소 / 환불 / 보증금예치 / 보증금차감 / 보증금환급
  • 월 마감 취소는 슈퍼관리자 권한으로 제한하고 사유 입력 필수화

기대 효과: 금액 변동 경로 추적 가능. 오입력 정정 시에도 원본 기록 보존

2. 다중 운영사 구조

  • 하나의 시스템에서 복수 운영사가 각자의 건물을 관리하는 구조
  • 1차 운용 단계에서 운영사 3개를 실제로 운영 — 실 데이터 1개, 검증용 가상 데이터 2개
  • 격리는 데이터베이스 수준에서 강제. 응용 프로그램의 조회 조건에 의존하지 않음
  • 역할 3종 — 시스템 운영자 / 슈퍼관리자(운영사당 1명) / 관리자(담당 건물 배정)
  • 1차 제외: 가입 절차 · 요금제 및 과금 · 사용량 통계 · 운영사별 화면 테마

기대 효과: 검증용 운영사에서 실 데이터를 건드리지 않고 청구·마감·해지 시험 가능. 격리 결함을 외부 운영사 수임 전에 발견. 구조를 사후 추가하려면 전체 테이블 변경을 수반하므로 1차 확보가 총비용 측면에서 유리

3. 인프라 선정

  • 데이터베이스 — Supabase · 서울 리전. 인증·파일 저장·백업·격리 기능 포함
  • 인증 — Supabase Auth. 2단계 인증·초대 메일·계정 잠금을 직접 개발하지 않음
  • 네트워크 — Cloudflare. 웹 공격 차단 및 봇 차단 적용 (기 사용 중)
  • 도메인 — brikka.co.kr. 청구서 발송용 발신 도메인 인증 필요
  • 복구 목표 — 데이터 유실 허용 24시간 / 복구 소요 4시간

기대 효과: 인증·파일 접근 제어 직접 개발 제외로 개발 기간 2~3주 단축. 국내 리전 사용으로 개인정보 국외 이전 문제 미발생

4. 신규 개발 확정

  • 기존 시스템의 코드를 계승하지 않음
  • 근거 1 — 1차 범위의 핵심인 청구·수납·원장·정산이 기존 코드에 부재. 기존 구현은 건물·유닛·계약의 등록과 조회까지
  • 근거 2 — 원장 중심 구조와 다중 운영사 구조가 기존 구조와 양립 불가
  • 근거 3 — 재사용 가능 범위 산정 결과 3~5일 분량. 화면 구성요소 51종은 공개 표준 모음이며 재설치 가능

기대 효과: 운영 중인 데이터가 없어 데이터 이관 작업 미발생. 개발자 견적에서 해당 항목 제외. 기존 코드 하자에 대한 책임 소재 논쟁 차단

개발자가 캐나다 거주 프리랜서일 가능성에 따른 선행 작업 — 세부내용 하단 참조

‣ 목업 제작 계획

  • 대상 — 35개 전체가 아니라 복잡도가 높거나 판단이 필요한 10~15개. 목록 형태가 반복되는 화면은 대표 1개로 갈음
  • 형태 — 실제 화면과 동일한 배치. 메뉴 클릭 시 화면 전환. 데이터는 가상 입력
  • 검증 항목 — 항목 수가 화면에 수용되는지, 조작 동선이 실제 업무와 맞는지, 표의 열 구성이 적정한지
  • 제작 순서 — 어려운 화면부터. 단순 목록 화면에서는 문제가 드러나지 않음

기대 효과: 명세 해석 차이로 인한 재작업 방지. 목업 단계의 수정 비용은 사실상 없으나 개발 착수 후 변경은 코드 수정을 수반

‣ 산출물 번역 계획

배경

  • 개발 담당자가 캐나다 거주 프리랜서 개발자일 가능성이 높음
  • 현재 산출물은 전량 한국어. 기능정의서 12개 문서 5,082행
  • 상업용 임대차 용어(전용면적·관리비·보증금·안분·원장 등)는 일반 번역으로 처리 시 의미 왜곡 우려

진행 방식

  • 1단계 한영 용어집 선행 작성
    • 청구 항목 19종, 상태값, 거래유형 8종, 화면명 등 고정 용어를 먼저 확정
    • 용어집은 번역물일 뿐 아니라 개발 산출물에 해당. 테이블명·변수명이 여기서 파생되므로 사후 변경 시 코드 전반에 영향
  • 2단계 범위 파악용 요약본 번역 — 개발자 접촉 시점에 제시할 개요·범위·구조
  • 3단계 전문 번역 — 계약 확정 후. 목업 반영으로 명세가 확정된 이후 착수하여 재번역 방지

기대 효과: 용어 불일치로 인한 구현 오류 방지. 명세 확정 후 번역하여 동일 문서의 반복 번역 회피
