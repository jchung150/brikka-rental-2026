## 3. 작업 프로토콜 (그대로 유지할 것)

**순서**: 기능정의서 ID 순 (PRO → CTR → PAY → REQ → RES → REC → REP → USER → OWN → TEN → DOC → NTF → DASH)

**한 행마다 Claude가 제시할 것**
1. 📄 원 명세 요약
2. 🔍 실제 구현과의 차이
3. 🏢 상업용 쟁점
4. ❓ 결정할 항목 + **각각에 대한 Claude의 제안**

**대표가 동의/수정 → Claude가 수정된 행을 컬럼별로 제시 → 대표가 엑셀에 직접 반영**

### 문서 작성 규칙 (중요)
- **`비고` 칼럼 = 사양만.** "A에서 B로 바꿨다" 같은 변경 이력을 적지 않는다. 히스토리는 git이 담당한다.
- **`고민되는 점` 칼럼 = 질문 `(이어서)` 결론.** 원문서의 기존 규칙이며 판단 근거는 여기에 쌓는다.
- **예외**: `[2차]` 같은 범위 결정은 개발자가 지금 알아야 할 지시이므로 `비고`에 남긴다.
- 결정할 게 없는 행은 "넘어가도 됩니다"라고 표시한다.

### ⚠️ git 사용 규칙 (2026-09-19 지시)
- **커밋은 해도 되지만 `git push`는 사용자 허락을 받고 한다.** 작업이 끝나면 커밋까지만 하고 푸시 여부를 묻는다.

### ⚠️ 코드 분석에 대한 지시 (2026-09-12 추가)
- **기존 앱 코드는 분석하지 않는다.** 기능 정의에 집중한다. **스키마(`schema.prisma`)는 참고해도 좋다.**
- 이유: 코드 수정 사항이 이미 너무 많아 기존 코드를 기준으로 삼는 것이 시간 낭비다.

### ⚠️ 스키마 접근 방침 (2026-09-12 결정)
- **기존 스키마의 구조는 가져간다.** 버리지 않는다.
  - 근거 ①: 감사 결과 스키마가 저장소에서 가장 멀쩡한 부분이다.
  - 근거 ②: 건물 → 유닛 → 계약 → 청구 → 수납 골격은 상업용에서도 동일하다.
  - 근거 ③: **마이그레이션 이력이 없다**(`pnpm migrate` = `db push`). 스키마를 고치는 것과 새로 쓰는 것이 기계적으로 같은 작업이라, "수정이 많다"는 부담이 실제 비용으로 이어지지 않는다.
- **단, 결과물은 새로 쓴다.** 72행 검토가 끝난 뒤 패치를 하나씩 적용하지 않고 **`schema.prisma` 전문을 한 벌 새로 작성**한다. 기존 구조와 `스키마정의서`를 펼쳐놓고 쓰므로 빠지는 것이 없다.
- 따라서 **아래 7장(누적 스키마 변경)은 대표가 읽고 판단할 표가 아니다.** 최종 설계 시 Claude가 쓸 재료 메모일 뿐이다.
- **운영 데이터는 없다** (2026-09-12 확인). 스키마를 어떻게 바꾸든 데이터 이전 비용이 발생하지 않는다.

## 4.2 오픈 범위 — 1차 / 2차 구분

> 행별 검토에서 `[2차]`로 미룬 것을 모은 표다. **새 행을 검토할 때 여기에 계속 추가한다.**
> 원칙: **1차는 관리자(백오피스)가 혼자 운영할 수 있는 최소 범위.** 임대인·임차인이 직접
> 쓰는 화면과, 외부 서비스(PG·알림톡·국세청) 연동은 2차로 미룬다.

| 영역 | **1차 (초기 오픈)** | **2차** |
|---|---|---|
| **사용자** | 관리자 백오피스 (슈퍼관리자 단독 운영 전제) | 임대인 포털 / 임차인 포털 전체 · 관리자 권한 세분화 (G-4) |
| **건물·유닛** | 건물·유닛 등록/조회/수정, 공용시설, 주차면, 자료보관, 건물별 청구 항목 설정, 유닛 검침 설정 | — |
| **계약** | 계약 등록/조회/수정, 재계약, 해지, 임대조건 조정 일정(수동 적용) | 임대조건 자동 인상 적용 · 계약 "복사해서 새로 만들기" |
| **청구** | 청구 스케줄, 건물 관리비 정산(안분 계산), 청구서 발행, 원장(수익·부채 2계정) | — |

| **연체** | 연체료 계산 표시 + 수동 청구 | 연체료 자동 청구 |
| **발송** | **이메일만** — 청구 내역서 발송, 미납 독촉 일괄 발송, 웰컴 메시지 | **알림톡 전체** · 자동 발송 규칙 · 템플릿 관리 · 발송 이력 · 알림 채널 설정(알림톡/이메일/둘다/수신거부) · 건물·계약의 메시지 발송/수신 이력탭 |

### 1차에서 수동으로 남는 작업 (운영 부담)

PG 연동이 2차이므로 **입금 확인이 자동으로 되지 않는다.** 1차 운영은 이렇게 돈다:

```
25일   청구서 발송 (시스템)
26일~  임차인이 은행으로 입금
       관리자가 은행 거래내역을 확인
       → 시스템에서 [일괄 수납 처리] → 수납일·수단·입금자명 입력 → 원장에 기록
```

- 유닛 20개 건물이면 월 20~40건 수준. 건물이 늘면 부담이 커진다.
- **은행 거래내역 CSV 업로드 + 자동 매칭**이 PG 없이 이 부담을 크게 줄이는 방법이며 **PAY-6에서 1차 범위로 확정**했다. 입금자명 별칭 기반 매칭이라 쓸수록 자동화율이 올라간다.
- 상업용은 임차인이 **청구서 합계를 한 번에 입금**하므로, 수납 처리는 **입금 한 건을 여러 청구 항목에 배분**하는 2단 구조다. **PAY-6에서 확정**했다.

### PG사 선정 체크리스트 *(2차 착수 시)*

개발사가 없으므로 대표가 직접 비교해야 한다. PAY-7에서 도출한 확인 항목이다.

```
□ 가상계좌 발급 단위    계약당 고정 계좌인가, 건별 일회성인가
□ 부분입금 허용         청구액보다 적게 입금할 수 있는가 (막히면 부분납 처리가 불가능하다)
□ 입금자명 전달         가상계좌 입금 시 실제 입금자명이 넘어오는가
□ 웹훅 재전송·멱등키    중복 방지를 PG가 지원하는가
□ 수수료               가상계좌 건당 / 카드 요율
□ 정산 주기            입금일 → 실제 계좌 입금까지 며칠
□ 테스트 환경          개발·검증용 샌드박스 제공 여부
□ 정산 계좌 요건 ★     건물마다 운영계좌가 다른데 하나의 가맹점에서 건물별 계좌로 나눠
                      정산이 되는가. 불가능하면 건물마다 가맹점을 따로 개설해야 하며
                      수수료와 계약 조건에 직접 영향을 준다.
```

### 개발 착수 시 준비물 *(기능정의서 범위 밖)*
- **시드 스크립트가 없다.** `packages/database/prisma/`에 `schema.prisma` 하나뿐이고 시드·목 데이터 파일이 없다. 개발·테스트를 하려면 건물·유닛·계약·청구·수납 샘플 데이터를 넣는 스크립트가 필요하다. (2026-09-19 시점 "아직 필요 없음"으로 확인)

-유닛주소는 건물주소와 유닛고유번호를 조합해 표시하며 유닛별로 따로 입력하지 않는다.
-전용률 = 전용면적 ÷ 임대면적. 자동으로 계산해 표시하며 직접 입력하지 않는다.
-임대면적, 전용면적 단위는 제곱미터 단위로 입력한다.
-유닛상태는 계약 상태와 자동으로 연동된다.
 진행중 = 사용중 / 계약없음·준비중·종료됨·파기됨 = 공실.
 진행중은 보증금 전액 입금이 완료된 상태를 뜻하므로 이 시점부터 사용중으로 본다.
 임차인이 진행하는 인테리어 공사 기간도 사용중에 포함된다.
 계약금만 입금된 준비중 상태는 공실로 본다.
-비운영중은 임대 대상이 아닌 유닛(관리사무소, 기계실, 건물주 직접 사용, 장기 대수선 등)에
 슈퍼관리자가 수동으로 지정하며, 공실률 계산에서 제외한다.
 수동 지정이 계약 상태 자동 연동보다 우선하므로, 비운영중인 유닛은 계약이 생겨도
 자동으로 사용중이 되지 않으며 슈퍼관리자가 비운영중을 먼저 해제해야 한다.
-공실률 = 공실 유닛 수 ÷ (전체 유닛 수 − 비운영중 유닛 수)
-유닛에는 기본적으로 검침기가 있다고 본다. 검침기가 없는 유닛만 항목별로 "없음"을 지정한다.
-기본 조정 배수는 계량기 모델 차이 등으로 사용량을 보정해야 할 때 사용한다. 기본값은 1.0이며
 한 번 바꾸면 다시 변경할 때까지 유지된다. 회차별로 다르게 적용하려면 정산 화면에서 조정한다.
-조정 배수는 해당 유닛의 정산 사용량 전체에 적용된다. 전용부 청구액과 공용 배분 비율에
 모두 반영되며, 배분 총액은 항상 고지서 금액과 일치한다.
-계약내역은 목록 형태로 표시되며 유닛과 연결된 모든 계약(과거부터 현재까지)을 볼 수 있다.
 계약 내역의 수정/추가/삭제는 불가하다.
-계약정보 목록에서 개별 계약을 클릭하면 계약의 상세 정보가 담겨있는 CTR-3로 이동한다.
-임대료와 관리비는 각각 구분해 월 금액으로 표시하며, 부가세 별도 금액으로 표시하고
 "(부가세 별도)"를 병기한다.
-[2차] 요청이력은 해당 유닛으로 등록된 요청을 조회만 하며, 등록/수정은 요청 관리 화면에서
 한다. 요청 관리(REQ 계열)와 함께 2차에 구현한다.
-메모는 단일 입력 항목이며 작성자·작성 이력을 따로 남기지 않는다.
-썸네일용 사진은 1개만 업로드한다.
-계약 이력이 하나라도 있는 유닛은 삭제할 수 없다. 계약이 전혀 없는 유닛만 삭제 가능하며,
 사용하지 않는 유닛은 비운영중으로 지정한다.
-가전제품 및 가구 섹션은 사용하지 않는다. (PRO-2 참조)
```

**【고민되는 점】** *(신규 — 원문 비어 있었음)*
```
-유닛상태에 "예약중"과 "공사중"이 필요한가?
 (이어서) 필요 없다. 상업용은 임차인이 계약을 체결한 뒤 직접 인테리어 공사를 하므로
 계약이 진행중이 된 시점부터 사용중으로 본다. 공실/사용중/비운영중 3가지로 한다.
-계약 상태 "준비중"(날인 전, 가계약금만 입금된 상태)을 사용중으로 볼지 공실로 볼지?
 (이어서) 공실로 본다. 임대료가 발생하지 않는 상태이므로 공실률에 공실로 집계해야
 임대인 보고 수치가 실제 임대수익과 어긋나지 않는다. 계약이 잡혀 있다는 사실은
 유닛 목록의 임차인명으로 확인할 수 있어 유닛상태를 따로 나눌 필요가 없다.
-메모를 작성자·등록일시가 남는 목록 형태로 관리할지?
 (이어서) 단일 입력 항목으로 한다. 초기 오픈 범위에서 이력 관리까지는 필요하지 않다.
-임대료와 관리비를 합산해 보여줄지 구분할지, 부가세는 포함할지 별도로 할지?
 (이어서) 임대료와 관리비를 구분하고 부가세는 별도로 표시한다. (CTR-1 참조)
-과거 계약 이력이 있는 유닛을 삭제하면 계약 이력도 함께 사라지는데 삭제를 허용할지?
 (이어서) 계약 이력이 있으면 삭제를 막고 비운영중으로 지정한다.
-유닛 상세에 요청 이력을 보여줄 필요가 있는지?
 (이어서) 상업용은 유닛 단위 시설 요청이 잦으므로 조회 전용으로 표시한다.
```

**【입출력 데이터】**
```

**【비고】**
```
-계약 상태 정의는 다음과 같다.
준비중: 계약금만 입금되어 유닛을 선점해 둔 상태. 임차인이 아직 공간을 사용하지 않으며
        임대료도 발생하지 않는다.
진행중: 보증금 전액 입금이 완료되어 계약이 개시된 상태. 이 시점부터 임차인이 공간을
        사용할 수 있으며, 임차인이 진행하는 인테리어 공사 기간도 여기에 포함된다.
종료됨: 계약 만료가 되어 정상적으로 종료된 상태
파기됨: 분쟁, 위반 등의 이유로 계약이 강제 종료되거나 무효 처리된 상태

-계약금은 보증금의 선입금분으로 보며 별도 항목으로 관리하지 않는다.
 보증금 전액이 입금되어야 진행중으로 전환한다.

-계약시작일은 계약 기간의 시작일이며 유닛상태, 공실률, 계약만료남은일수의 기준이 된다.
 임대료와 관리비의 청구 시작일(기산일)은 계약시작일과 별개로 관리하며,
 기산일이 계약시작일보다 앞설 수도(소급) 뒤설 수도(렌트프리) 있다.

-계약고유이름은 3개의 데이터 필드가 조합된 구조로 자동으로 생성된다.
(예: 역삼 브리카타워 | 8층 전체 | (주)한빛)

-계약조건은 데이터 필드가 조합된 구조로 자동으로 생성된다.
(예: 2025.08.13 - 2026.08.12 | 보증금 1억 | 임대료 700만원 | 관리비 180만원)

-임대료와 관리비는 부가세 별도 금액으로 표시하고 "(부가세 별도)"를 병기한다.
 보증금은 부가세 표기 대상이 아니다.

-기산일이 계약시작일과 다른 경우에만 해당 금액 옆에 기산일을 병기한다.
(예: 임대료 700만원 (2025.08.01부터))

-렌트프리 중인 계약은 금액 옆에 "렌트프리 중" 배지를 표시한다.
 렌트프리 중 = 계약시작일 ≤ 오늘 < 임대료 기산일. 별도 항목으로 입력받지 않는다.

-계약만료남은일수는 계약종료일을 기준으로 계산한다. 갱신 통지 마감일을 별도로 두지 않으며
 목록에 갱신 통지 관련 항목을 표시하지 않는다.

-남은 일수에 따라 다른 색을 사용한다. 예를 들어 남은 일수가 30일이하면 중요도가 높음을
 나타내는 빨간색으로 표시
-남은 일수에 내림차순/올림차순 기능을 적용한다.

-개별 계약 클릭시 상세 페이지(CTR-3)으로 이동한다.
-상단에 "새로운 계약 등록" 버튼이 있다.

-목록의 마지막 컬럼에 더보기 액션 메뉴(케밥메뉴)를 추가한다.
계약상세보기, 재계약하기 (진행중 상태에서만 활성화), 계약상태변경, 계약해지, 계약삭제
(계약해지와 계약삭제는 CTR-3 비고 섹션 참고)

-계약상태를 변경하면 해당 유닛의 유닛상태가 자동으로 연동된다. (PRO-4 참조)
```

**【고민되는 점】**
```
-만료를 앞둔 계약만 따로 볼 수 있도록 하려면 어떻게 화면 구성을 할 것인지?
(이어서) 대시보드에 만료를 앞둔 계약은 90일(00개)/60일(00개)/30일(00개)로 보여주고
클릭하면 필터가 자동 적용된 계약 정보 조회화면으로 이동함.

-조회 화면에서 계약시작일, 종료일 이렇게 단순하게 보여주면 직관적이지 않음. (UX)
(이어서) 연관있는 정보를 한 곳에서 보여주도록 조합 구조로 변경

-더보기 액션 메뉴에서 "복사해서 새로 만들기" 기능을 넣으면 관리자 입장에서 템플릿으로
활용할 수 있으므로 매우 편리함.
(이어서) 다음 Phase에 고려

-갱신 통지 마감일을 계약 종료일과 별도로 관리해야 하는가?
(이어서) 관리하지 않는다. 마감일을 따로 두면 종료일과 두 개의 날짜를 동시에 보게 되어
오히려 헷갈린다. 계약 종료일 하나를 기준으로 남은 일수를 계산하고, 갱신 문의는
운영상 종료 한 달 전에 진행한다.

-계약 개시 기준을 계약서 날인으로 볼지 입금으로 볼지?
(이어서) 보증금 전액 입금으로 본다. 현장에서는 계약금만 들어온 상태에서 임차인이
공간을 쓰지 않으며, 보증금이 들어오는 날이 실질적인 계약 시작일이다.

-계약서상 계약시작일과 임대료를 받기 시작하는 날이 다른 경우가 있다.
(예: 임차인 사정으로 8/13에 계약을 맺었으나 임대료는 8/1부터 소급 계산)
(이어서) 계약시작일과 청구 기산일을 분리한다. 계약시작일은 계약 기간·유닛상태·공실률의
기준으로 쓰고, 임대료·관리비는 각각 기산일을 따로 갖는다. 이 구조로 소급과 렌트프리가
모두 표현되므로 렌트프리를 별도 항목으로 두지 않는다.
기산일이 다른 경우는 드물므로 등록 화면에서는 체크박스로 열어 입력한다.

-계약상태 라벨을 화면에서 "계약중/계약완료/계약종료/계약해지"로 쓸지?
(이어서) "준비중/진행중/종료됨/파기됨"으로 통일한다. "계약완료"가 진행중을 뜻하면
종료된 계약으로 오해하기 쉽다.

-목록의 금액을 총액 하나로 보여줄지 임대료와 관리비를 나눌지?
(이어서) 임대료와 관리비를 구분해서 표시한다. 상업용은 두 금액의 비중과 인상 시점이
달라 합산하면 판단이 어렵다.
```

-수정 가능한 것 vs. 수정 불가능한 것
(이어서) 유닛고유번호 수정 불가 - 계약 식별자이며, 건물-계약-청구를 연결하는 주요 키이기
때문에 데이터 연결이 무너질 수 있다. 계약시작일 수정 불가 - 이미 시스템에 의해 자동으로 청구가
자동 생성되기 때문에, 시작일을 임의로 변경하면 기존 청구 스케줄과 충돌한다. 계약 상태 수정
제한 - 수동 수정은 허용하되만, 경고 메시지 알림이 필요하다.
(이어서) 계약시작일과 청구 기산일을 분리했으므로(CTR-1 참조) 계약시작일을 고쳐도 청구
스케줄과 충돌하지 않는다. 계약시작일은 경고와 함께 수정을 허용하고, 유닛고유번호만 수정
불가로 유지한다.

-계약 정보 수정 내용을 임차인에게 알릴 것인가?
(이어서) 내용에 따라 다르다. 예를 들어 단순 오타 수정은 임차인에게 알릴 필요 없지만, 계약
조건(임대료, 계약기간 등) 실질적인 계약 내용의 변경은 임차인에게 알려야 한다.
(이어서) 임차인에게 알릴만한 수정 사항이 자주 발생하지는 않을 것. 발생한다면 수동으로
알림톡을 전송하는 방법이 나을 듯 하다.

-삭제를 해도 괜찮은가?
(이어서) 삭제를 하면 이 계약과 연결된 청구 스케줄도 함께 삭제되어야 하기 때문에 신중해야
한다. 따라서, 삭제 전에 모든 청구 스케줄을 삭제해야 한다. 또한 해당 계약이 기존 계약에서
연장된 계약이라면 기존 계약에도 연관을 줄 수 있기 때문에, 삭제해서는 안된다.
(이어서) 슈퍼관리자에 한해서 조건부 삭제가 가능하도록.

-계약 상태 수정 워크플로우 및 경고 메시지
(준비중->진행중)
메시지: "보증금 전액 입금이 완료되었습니까? 진행중으로 변경하면 청구 스케줄이 시작됩니다.
청구서 발송은 별도로 진행됩니다."
(준비중->파기됨)
메시지: "아직 진행되지 않은 계약을 파기 처리하려 합니다. 이 작업은 되돌릴 수 없습니다.
계속하시겠습니까?"
(진행중->준비중)
메시지: "진행 중 계약을 준비 상태로 되돌리면 청구 스케줄이 중단되며, 다음 납부 마감일에
청구서가 발송되지 않습니다. 계속하시겠습니까?"

메시지: "계약 해지 처리로 진행됩니다. 해지일 이후의 청구 스케줄이 중단되며, 보증금 정산은
원장에서 처리합니다. 계속하시겠습니까?"
(진행중->파기됨)
메시지: "계약을 파기 처리하면 해지일 이후의 청구 스케줄이 중단되며, 계약은 무효로 처리됩니다.
이 작업은 되돌릴 수 없습니다. 진행하시겠습니까?"
(종료됨->준비중/진행중/파기됨) -> 불허
메시지: "종료된 계약은 상태 변경이 불가능합니다. 새로운 계약을 생성하세요."
(파기됨->준비중/진행중/종료됨) -> 불허
메시지: "파기된 계약은 상태 변경이 불가능합니다. 새로운 계약을 생성하세요."

-계약 해지는 어떻게 처리하며, 종료됨과 파기됨은 어떻게 구분하는가?
(이어서) 해지 시 해지유형을 먼저 고르고 유형에 따라 상태를 정한다. 만기 종료와 합의 중도
해지는 종료됨, 위반·분쟁에 의한 해지는 파기됨이다. 합의 해지에 파기됨을 붙이면 어감이 나쁘고
이력에도 그대로 남으므로 구분한다. 퇴거 정산은 원장의 보증금차감·보증금환급 거래로 처리하므로
별도 화면이 필요 없다.

-원장에서 부가세를 어떻게 기록하는가?
(이어서) 상업용은 세금계산서 발행이 전제이므로 공급가액과 부가세를 구분해야 한다. 거래 한
줄에 공급가액·부가세·합계를 함께 기록한다. 별도 줄로 나누면 세금계산서 한 건이 원장 두 줄이
되어 대사가 어려워진다.

-요약탭의 잔액을 하나로 보여줄지 둘로 나눌지?
(이어서) 원장에서 수익계정과 부채계정을 합산하지 않으므로 표시도 나눈다. 미수금 잔액과
보증금 잔액을 나란히 표시한다.
```

**【설명】** 진행중인 계약을 불러와 임대인과 임차인이 합의한 새 조건으로 연장 계약을 등록한다.

```

**【비고】**
```
-재계약은 임대인과 임차인이 합의한 새 조건을 담는 기능이다. 재계약 합의서 발송과 확인·날인은
 시스템 밖에서 진행하며, 합의가 끝난 뒤 관리자가 재계약을 등록한다.
-재계약 버튼은 진행중인 계약에서 언제든 활성화된다.
 (입주 도중 조건을 바꾸는 경우, 만기 직전에 연장하는 경우 모두 포함)

-기존 계약과는 별도의 새로운 계약ID를 가지며, 기존 계약과 연결된다.
-필드 구성은 CTR-2와 같으며 기존 계약의 값이 미리 채워져 있다. 주로 수정하는 항목은
 계약기간, 임대료, 고정관리비, 보증금이다.

-계약 시작일 기본값은 기존 계약종료일 다음날이며 수정할 수 있다. 기존 계약 기간 중의 날짜로
 정하면 기존 계약의 종료일이 새 계약 시작일의 전날로 자동 조정된다.
 (한 유닛에 진행중 계약이 겹치지 않도록)
-계약 종료일 기본값은 계약 시작일로부터 2년 후의 전날이며 수정할 수 있다.

 같은 임차인이 계속 사용하므로 보증금 입금 여부와 관계없이 전환하며, 유닛상태는 사용중을

 "재계약 승계" 거래로 표시한다. 증액분은 연장 계약에 보증금 청구로, 감액분은 보증금 환급으로
 기록한다.

-[2차] 가상계좌는 PG 연동 시 기존 계약의 가상계좌를 승계한다.

(이어서) 아니다. 같은 임차인이 끊김 없이 계속 쓰는 것이므로 새 계약 시작일에 자동으로

(이어서) 표시하지 않는다. 협상 중에 숫자가 계속 오르내려 고정 표시가 의미가 없다. 계산기
위젯도 따로 만들지 않는다. 일반 계산기를 쓰는 편이 빠르다.

-월단위갱신계약도 재계약 대상인가?
(이어서) 계약유형에서 월단위갱신계약을 뺀다. 한국에서 월 단위로 계약서를 만드는 경우는 드물다.
```

**【고민되는 점】**

원장을 개발한다. 원장 구조는 CTR-3 원장정보탭에 정의한다.

-이 화면이 약정(청구 스케줄)을 보여주는 곳인가, 회차별 실제 청구를 보여주는 곳인가?
(이어서) 약정을 보여주는 곳이다. 정산 항목은 약정액이 없으므로 이 화면만으로는 실제 청구액을
알 수 없다. 회차별 실제 청구와 수납 현황은 PAY-2에서 본다. 화면 이름도 "청구 스케줄 조회"로
바꾼다.

-연체료를 시스템이 자동으로 계산하고 청구해야 하는가?
(이어서) 계산은 하되 자동 청구는 하지 않는다. 며칠 늦은 정도는 실무에서 받지 않고 넘어가는
경우가 많아 자동으로 붙으면 임차인과의 관계가 불편해진다. 연체이자율은 연 8%를 기본값으로
계약에 등록해 두고, 받을지 여부는 관리자가 판단한다.
```

### PAY-2 · 청구·수납 현황

> **【기능(분류:중)】 이름 변경**: `미납 내역 조회` → **`청구·수납 현황`**

**【입출력 데이터】**
```
필터: 건물고유이름, 계약상태(디폴트: 진행중), 납부상태(디폴트: 납부전 + 부분납)

[목록] - 청구별 체크박스가 있어 일괄 처리와 이메일 발송에 사용한다
(체크박스)
계약고유이름(건물고유이름, 유닛고유번호, 대표임차인명)
계약상태(준비중/진행중/종료됨/파기됨)

납부상태(납부전/부분납/완납/무효)
연체일수
연체료(예상)
더보기(수납기록생성, 계약정보, 임차인정보)

[계약별 소계] 계약고유이름, 미납 건수, 미납액 합계
```

**【비고】**
```
-수납액은 임차인에게서 현재까지 받은 금액이다. 미납액 = 청구액 − 수납액이며,
 미납액이 0이 되면 납부상태가 완납으로 바뀐다.

-납부상태는 금액 기준으로만 판단한다. 기한 경과 여부는 연체일수 칸에서 따로 본다.
 납부전 - 수납액이 0인 상태
 부분납 - 수납액이 있으나 미납액이 남은 상태
 완납   - 미납액이 0인 상태
 무효   - 청구가 취소된 상태
-미납 = 납부상태가 납부전 또는 부분납인 건. 연체 = 그중 연체일수가 1일 이상인 건.
-"미납만 보기" 버튼은 납부상태 납부전 + 부분납으로 필터를 건다.
-기본 필터는 미납(납부전 + 부분납)이며, 납부상태 필터를 풀면 완납 건을 포함한 회차별 전체
 청구·수납 현황이 된다. "미납만 보기" 버튼으로 언제든 기본 상태로 돌아온다.
 회차별로 누가 얼마를 내야 하고 얼마를 냈는지 보는 화면이 이 화면이다. (PAY-8 참조)
-연체일수 = 오늘 − 납부마감일. 마감일이 지나지 않았으면 "-"로 표시한다.

-이 화면의 금액은 부가세를 포함한 합계 기준으로 표시하며, 공급가액과 부가세를 함께 보여준다.
 실제로 받아야 할 금액을 보는 화면이고 세금계산서와 대조할 수 있어야 하기 때문이다.
 (약정액을 보는 화면인 CTR-1, PAY-1은 부가세 별도로 표시한다)

-연체료(예상) = 미납액(부가세 포함) × 연체이자율 × 연체일수 ÷ 365
 연체이자율은 계약에 등록된 값을 사용하며 기본값은 연 8%다. (CTR-2 참조)
-연체료는 표시만 하며 자동으로 청구하지 않는다. 해당 건을 선택하고 "연체료 청구"를 누르면
 연체료 청구 항목이 생성되고 원장에 청구 거래로 기록된다. 연체료는 과세 항목이다.

-상단에 "일괄 수납 처리" 버튼이 있다. 해당하는 청구를 선택하고 누르면 수납일,
 수납수단(계좌이체/카드/현금/상계), 입금자명을 입력받아 원장에 수납 거래로 기록한다.
 납부상태를 직접 바꾸는 것이 아니라, 거래를 기록하면 납부상태가 따라온다. (PAY-6 참조)
-상단에 "연체료 청구" 버튼이 있다.
-상단에 "이메일 일괄 발송" 버튼이 있다. 선택한 미납 건의 내역을 담은 독촉 메일을 임차인
 담당자에게 발송한다.
-상단에 "미납만 보기" 버튼이 있다.
-[2차] "알림톡 일괄전송"은 알림 발송 기능(NTF) 정비 시 함께 구현한다.

-드롭다운 메뉴에서 건물고유이름을 선택한다.
-체크박스 메뉴에서 계약상태와 납부상태를 선택한다.
-계약별로 그룹핑하고 계약별 미납 소계를 표시한다. 한 임차인이 여러 항목을 밀린 경우
 받아야 할 총액을 바로 확인할 수 있어야 한다.
```

**【고민되는 점】**
```
-완납처리를 관리자가 사용해도 괜찮을지? 보안상의 문제는 없을지 고민해 보아야 한다.
(이어서) 결산을 해 보았을 때 모든 임대료가 완납이어도 실제 받은 금액은 완납이 아닐 수 있다.
현재 원장 기능이 없기 때문에 정확히 받은 금액이 얼마인지 확인하기가 어렵다.
(이어서) 원장을 도입하면서 해소됐다. 상태를 직접 바꾸는 "완납 처리"를 없애고, 수납 거래를
기록하면 납부상태가 따라오는 "일괄 수납 처리"로 바꾼다. 장부에 없는 돈이 생길 수 없다.

-부분납을 납부상태에 어떻게 표시할 것인가?
(이어서) 납부상태는 금액 기준(납부전/부분납/완납/무효)으로만 판단하고, 기한 경과는 연체일수로
따로 표시한다. 기존의 "미납"은 금액과 시점 두 가지를 섞고 있어 부분납이 들어갈 자리가 없었다.

-미납 화면의 금액을 부가세 별도로 볼지 포함으로 볼지?
(이어서) 부가세 포함 합계 기준으로 본다. 실제로 받아야 할 금액을 보는 화면이기 때문이다.
약정액을 보는 화면과는 기준이 다르다.

-연체료를 어떤 금액에 매기고 부가세는 어떻게 처리하는가?
(이어서) 부가세를 포함한 미납액에 매기며, 연체료 자체도 과세로 처리한다.
```

**【알림 트리거】** 알림톡 `[2차] 미납 독촉 일괄 발송` / 이메일 `미납 독촉 일괄 발송` / 내부 알림 `없음`

### PAY-3 · 청구 스케줄 생성

**【입출력 데이터】**
```
생성:
청구항목(G-13 기준표, 새롭게등록가능)
산정방식(고정액/정산)
청구액 — 고정액 항목만 입력한다. 정산 항목은 PAY-10에서 산출한다.
메모
반복주기(이번만/매월/격월/분기/반기/연1회)
부가세대상여부(과세/면세, 디폴트: 과세)
청구알림설정(00일 전에 보내기)
반복종료조건(계약종료시까지 / 00번반복후종료(횟수지정))
우선순위(수납 처리 시 우선순위대로 수납액을 분배함)

※ 청구일과 납부마감일은 계약 단위로 관리한다. (건물 기본값을 계약이 상속)
```

**【비고】**
```
-청구 스케줄 등록은 계약 상태가 "준비중"일 때도 가능하다. 다만 실제 청구 회차는 계약이
 "진행중"이 된 뒤부터 생성된다. 보증금 입금 전에 청구서가 나가지 않도록 한다.
-반복 항목은 청구일에 맞춰 백그라운드 스케줄러가 회차를 생성한다.
-고정액 항목(임대료, 고정관리비)은 금액이 정해져 있으므로 스케줄러가 자동으로 회차를 만든다.
 정산 항목(전기·수도·주차 등)은 건물 관리비 정산(PAY-10)에서 금액이 확정될 때 회차가
 만들어진다. 두 항목은 같은 청구년월로 묶여 한 장의 청구서가 된다.
-관리자가 임의로 스케줄을 중지할 수 있다.

-반복 스케줄을 수정할 때 적용 범위를 고른다. "이 항목만 수정" / "이후 반복 모두 수정" /
 "전체 반복 수정"
-반복 스케줄을 삭제할 때 적용 범위를 고른다. "이 항목만 삭제" / "이후 반복 모두 삭제"
-이미 발행된 회차는 이 화면에서 바꾸지 않는다. 발행된 청구의 수정·무효 처리는 PAY-5에서 한다.
-스케줄 수정은 앞으로 생성될 회차부터 적용되며, 이미 발행된 회차에는 소급하지 않는다.
-스케줄 수정·삭제 시 누가, 언제, 무엇을 바꿨는지 이력을 남긴다.

-청구서는 회차(청구년월)마다 계약당 1장 발행하며 그 안에 항목별 명세를 담는다.
 원장에는 항목별로 청구 거래가 각각 기록된다. (CTR-3 참조)

-청구일과 납부마감일은 건물에 기본값을 두고 계약에서 덮어쓸 수 있다. 계약 단위로 하나씩만
 두며 청구 항목별로 따로 두지 않는다.
 (예: 8월분 임대료·관리비를 8월 19일에 청구하고 8월 31일까지 납부한다)
 건물 기본값을 바꾸면 그 이후 등록되는 계약에만 적용되며 기존 계약은 그대로 둔다.

-일할 계산은 해당 기간의 실일수를 기준으로 한다. 시작일과 퇴거일은 모두 포함한다.
 청구액 = 월 약정액 × 청구 대상 일수 ÷ 해당 기간 총일수
 (예: 임대료 700만원, 계약시작일 8/13 → 8/13~8/31은 19일, 8월은 31일 →
  7,000,000 × 19 ÷ 31 = 4,290,323원)

-계약이 시작된 회차의 청구일이 이미 지난 경우, 다음 회차 청구일에 청구서를 2장 발행한다.
 지난 회차의 일할분 청구서와 당월 전액 청구서를 각각 발행하며, 납부마감일은 둘 다 당월
 납부마감일로 한다.
 (예: 계약시작일 8/29, 청구일 매월 19일 → 9/19에 8월분 3일치 청구서와 9월분 전액 청구서를
  함께 발행하고 둘 다 9/30까지 납부한다)

-정산 항목에서 임차인이 산정 기간 중 일부만 사용한 경우(입주·퇴거), 담당자가 해당 유닛의
 금액을 직접 계산해 입력한다. 시스템은 검침과 안분까지만 자동으로 처리한다. (PAY-10 참조)
-공실 유닛도 공용분 안분 대상에는 포함하되 청구서를 만들지 않는다. 공실 기간의 요금은
 건축주가 부담하며 남은 임차인에게 전가하지 않는다. (PAY-10 참조)

-청구항목마다 우선순위가 존재한다. (예: 임대료=1, 고정관리비=2, 주차비=3)
-우선순위는 하나의 계약 내에서만 유효하며 다른 계약은 우선순위가 달라질 수 있다.
-우선순위 기본값은 임대료 1, 고정관리비 2, 주차비 3, 정산 항목 4부터이며 연체료가 마지막이다.
-수납액 배분 순서는 오래된 청구년월부터이며, 같은 회차 안에서는 우선순위가 낮은 번호부터
 채운다.
```

**【고민되는 점】** *(신규 — 원문 비어 있었음)*
```
-청구 스케줄을 계약 상태가 진행중일 때만 만들 수 있게 할 것인가?
(이어서) 등록과 발행을 나눈다. 스케줄 등록은 준비중에도 가능하고, 실제 청구 회차는 진행중이
된 뒤부터 생성된다. 계약 등록 화면에서 청구 항목을 함께 받기 때문이다. (CTR-2 참조)

-첫 달과 마지막 달을 어떻게 계산할 것인가?
(이어서) 해당 기간의 실일수를 기준으로 일할 계산한다. 30일 고정으로 하면 달마다 조금씩 더
걷혀 연간으로 어긋난다. 시작일과 퇴거일은 모두 포함한다. 퇴거 당일에 이사를 나가는 임차인이
많기 때문이다.

-계약 시작일이 그 달 청구일보다 늦으면 어떻게 하는가?
(이어서) 다음 회차 청구일에 청구서를 2장 발행한다. 지난 회차 일할분과 당월 전액을 각각
발행한다. 합산하지 않는 이유는 어느 달 요금인지 구분되어야 하기 때문이다.

-청구일과 납부마감일을 어디에 둘 것인가?
(이어서) 건물에 기본값을 두고 계약에서 덮어쓴다. 건물마다 청구 규칙이 다를 수 있고, 한 건물의

**【비고】**
```

 임차인이 입금했다고 주장하는데 데이터가 남아 있지 않으면 분쟁이 생긴다.

 은행거래내역매칭 - 수동 등록과 동일하게 취급한다. 관리자가 승인해서 들어온 기록이고 매칭

 [2차] PG자동     - 메모 외의 필드는 수정할 수 없다. 외부 시스템 기록이므로 고치면 PG 정산과
                  어긋난다. 무효 처리는 사유를 입력해야만 가능하다.
                  화면에 "자동 수납건은 수정 불가"라고 명시해 오해를 방지한다.

-무효 처리 시 함께 정리되는 것

 · 보증금 수납이었고 해당 계약이 진행중이면 "이 계약이 진행중 상태입니다. 계속하시겠습니까?"
   경고를 표시한다.
 · 관련 청구의 납부상태와 미납액을 자동으로 재계산한다.

-모든 변경 사항은 이력으로 보존한다. 누가, 언제, 무엇을, 왜 수정하거나 무효 처리했는지 남기며
 화면에서 조회할 수 있다.
```

**【고민되는 점】**
```
-수납 기록을 삭제한다면 회계적 보존에 문제가 있어 추후 분쟁 거리가 될 수 있음. 그렇다면,
이력을 남겨야 하는지?

(is_valid: true/false) 또한, 누가 언제 왜 삭제를 했는지 기록을 남겨야 함.
(이어서) 원장에 "수납 취소" 거래를 기록하는 방식으로 처리한다. 원 수납 거래를 지우지 않고
취소 거래를 쌓으므로 수납 → 취소 흐름이 장부에 그대로 남는다. (PAY-5의 청구 취소와 같은 원칙)

-자동 수납건도 수정/삭제 가능하게 할 것인지? No

불가로 두고, 은행 거래내역 매칭 건은 관리자가 승인해서 들어온 기록이므로 수동 등록과 동일하게

-입금액을 직접 고칠 수 있게 할 것인가?

-배분이 잘못된 경우에도 무효 처리를 해야 하는가?

흔하므로, 총액을 고정한 채 배분만 다시 짜게 한다.
```

### PAY-10 · 건물 관리비 정산 *(신규 행)*

> 기능정의서에 없던 신규 행이다. 2026-09-19 PAY 계열 ID 재정리 시 기존 최대 번호(PAY-9)
> 다음인 `PAY-10`을 부여했다. 엑셀에도 행을 새로 추가해야 한다.

**【기능(분류:대)】** 청구/수납 관리 · **【기능(분류:중)】** 건물 관리비 정산
**【설명】** 건물 단위로 공과금 고지서와 유닛별 검침값을 입력해 유닛별 청구 금액을 산출한다.
**【대상 사용자】** 슈퍼관리자, 관리자 · **【주요 액션】** 생성, 조회, 수정 · **【우선순위】** 매우 높음

**【입출력 데이터】**
```
필터: 건물고유이름, 정산회차(년월)

(고지서 입력)
[목록] 청구항목, 고지서 총사용량, 고지서 총금액(부가세 포함)
[전기 추가 입력] 공급가액, 부가세, 전력기금, TV수신료

(검침 입력)
[목록] 유닛고유번호, 청구항목, 검침일, 전월 검침값, 당월 검침값, 사용량(자동계산)
[입력시] 검침일, 당월 검침값
※ 검침 기록은 원본이며 수정하지 않는다.

(조정)
[목록] 유닛고유번호, 청구항목, 원본 사용량, 조정 배수, 정산 사용량, 사유, 작성자, 작성일시
[입력시] 조정 배수, 사유

(산출 결과)
[목록] 유닛고유번호, 임차인, 청구항목, 검침 사용량, 잔여 배분 사용량, 정산 사용량, 청구금액
합계 검증: 청구항목별 (임차인 청구액 합계 + 공실·미청구분 = 고지서 총금액) 일치 여부 표시

(정산 확정)
정산 확정 → 계약별 청구서 생성
```

**【비고】**
```
-임대료와 고정관리비는 계약 약정액이므로 이 화면에서 다루지 않는다. 사용량에 따라 금액이
 달라지는 항목만 정산한다.

-산정 규칙은 모든 항목에 동일하게 적용한다.
 1) 유닛 검침 사용량 = 당월 검침값 − 전월 검침값
 2) 정산 사용량 = 검침 사용량 × 조정 배수
 3) 잔여 사용량 = 고지서 총사용량 − Σ 정산 사용량
    (검침분을 임차인이 직접 납부하는 건물은 고지서가 이미 공용분이므로 잔여 = 총사용량)
 4) 가중치 = 배분 기준값(정산 사용량 또는 임대면적) × 조정 배수
 5) 잔여 배분 = 잔여 사용량 × (가중치 ÷ Σ가중치)   ※ 부담 대상 유닛에만
 6) 유닛 정산 사용량 합계 = 정산 사용량(청구하는 경우) + 잔여 배분
 7) 유닛 청구금액 = 고지서 총금액 × (유닛 정산 사용량 합계 ÷ 고지서 총사용량)
 8) 전력기금과 TV수신료도 같은 비율로 환산한다.

-검침 기록은 원본이며 수정하지 않는다. 보정이 필요하면 조정 배수를 별도 기록으로 남기고,
 사유와 작성자를 함께 저장한다. 조정은 해제할 수 있으며 회차별로 이력이 쌓인다.
-조정 배수의 기본값은 유닛에 설정된 기본 조정 배수(PRO-4)이며, 해당 회차에만 다르게 줄 수 있다.

-정산 확정 전까지 고지서 금액이나 검침값을 수정하면 전체가 재계산된다.
-확정 시 청구항목별로 (임차인 청구액 합계 + 공실·미청구분)이 고지서 총금액과 일치하는지
 검증하고, 일치하지 않으면 확정할 수 없다.
-공실 유닛도 공용분 안분 대상에는 포함하되 청구서를 만들지 않는다. 공실 기간의 요금은
 건축주가 부담하며, 남은 임차인에게 전가하지 않는다. 공실을 안분에서 빼면 공실이 늘수록
 남은 임차인의 관리비가 올라 분쟁 소지가 된다.
-산출 결과에 "공실·미청구분"을 별도 행으로 표시해 건축주 부담액을 확인할 수 있게 한다.
-임차인이 산정 기간 중 일부만 사용한 경우(입주·퇴거), 담당자가 해당 유닛의 금액을 직접
 계산해 덮어쓰고 사유를 남긴다. 시스템은 검침과 안분까지만 자동으로 처리하며 일할 계산은
 하지 않는다. 산정 기간이 달력 월과 어긋나는 경우(예: 매월 10일~익월 9일)가 많아 규칙으로
 고정하기 어렵다.

-정산 주기는 항목마다 다르다. (예: 전기요금 매월 / 상하수도요금 격월 /
 교통유발부담금 연1회 / 정화조청소비 반기) 해당 회차에 발생하는 항목만 정산한다.
-격월 또는 연 1~2회 발생하는 항목은 해당 회차에서 항목을 추가해 정산한다. 청구 주기를
 미리 고정하지 않는다.
-주차요금 중 방문 차량 요금은 경비원이 현장에서 계산한 결과를 유닛별 월 합계 금액으로
 입력한다. [2차] 입·출차 시간 기록과 시간제 자동 계산은 주차 관제 연동 시 검토한다.

-[2차] 세금계산서·계산서 발행과 은행 입금 확인은 초기 오픈 범위에서 제외한다.
 청구 내역서를 임차인 담당자 이메일로 발송하는 것까지가 초기 오픈 범위다.
```

**【고민되는 점】**
```
-공용 사용량을 배분할 때 특정 유닛에 배수를 적용하면 총액이 고지서와 어긋나지 않는가?
(이어서) 배수를 먼저 반영해 비율을 잡는다. 배분한 다음에 배수를 곱하면 합계가 고지서를
초과하게 되어 실제 낸 금액보다 더 걷게 된다. 배수를 먼저 반영하면 한 유닛이 더 내는 만큼
다른 유닛이 덜 내고 총액은 항상 고지서와 일치한다.

-계량기가 고장나거나 모델이 달라 사용량이 실제와 다를 때 검침값을 고쳐야 하는가?
(이어서) 고치지 않는다. 검침값과 사용량은 원본이므로 그대로 보관하고, 조정을 별도 기록으로
남긴다. 원본이 남아 있어야 나중에 금액 산출 근거를 추적할 수 있고 조정을 되돌릴 수 있다.

-조정 배수를 공용 배분에만 적용할지, 전용부 청구액까지 적용할지?
(이어서) 전용부와 공용 배분 모두에 적용한다. 조정의 의미를 "이 유닛의 사용량을 이만큼으로
본다" 한 가지로 통일하면 배수를 하나만 두어도 되고 총액도 항상 맞는다.

-검침기가 일부 유닛에만 있는 건물은 어떻게 배분하는가?
(이어서) 검침 가능한 유닛부터 사용량을 확정하고, 남은 사용량을 검침기 없는 유닛에 임대면적
비율로 안분한다. 검침기가 모두 갖춰진 건물은 남은 사용량이 순수 공용분이므로 전체 유닛에
검침 사용량 비율로 안분한다.
```

### 해소된 항목 *(참고 — 더 이상 미룬 상태가 아님)*
- `Company`를 "사업자 정보"로 재정의 + 사업자구분(법인/개인사업자) → **CTR-2에서 확정 (G-8)**
- `Lease.isCorporate` 제거 → **CTR-2에서 확정**
- 계약 등록 화면의 차량 정보 입력 제거 → **CTR-2에서 확정 (G-1)**
- 목록에서 임대료·관리비를 안정적으로 뽑는 방법 → **CTR-2에서 확정 (G-10, 고정액 항목으로 계약에 보유)**
- 계약 해지와 계약 삭제의 조건·차이 → **CTR-3에서 확정 (해지유형 3종으로 상태 결정)**
- 계약상태 용어 `파기됨` vs `해지됨` 통일 → **CTR-3에서 확정 (`파기됨` 유지, 합의 해지는 `종료됨`)**
- 임대조건 조정 일정의 "조정 적용하기" 동작 → **CTR-3에서 확정**
- 연체료 계산식과 청구 방식 → **PAY-2에서 확정 (연 8%, 부가세 포함 미납액 기준, 수동 청구)**
- 첫 달·마지막 달 일할 계산 → **PAY-3에서 확정 (실일수 기준, 시작일·퇴거일 모두 포함)**
- 입금 배분 규칙 → **PAY-3 + PAY-6에서 확정 (금액 정확 일치 우선 → 오래된 회차 → 우선순위 순)**
- 은행 거래내역 CSV 자동 매칭 1차 포함 여부 → **PAY-6에서 확정 (포함. 입금자명 별칭 기반)**
- 보증금 수납과 연동한 진행중 전환 → **PAY-6에서 확정 (자동 전환하지 않고 안내만)**
- 회차별 청구·수납 현황 화면 → **PAY-8에서 확정. PAY-8 재정의를 취소하고 PAY-2를 「청구·수납 현황」으로 확장** (PAY-8은 입금 건 조회로 유지)
