## 3. 작업 프로토콜 (그대로 유지할 것)

**순서**: 기능정의서 ID 순 (PRO → CTR → PAY → REQ → RES → REC → REP → USER → OWN → TEN → DOC → NTF → DASH)

**한 행마다 Claude가 제시할 것**
1. 📄 원 명세 요약
2. 🔍 실제 구현과의 차이
3. 🏢 상업용 쟁점
4. ❓ 결정할 항목 + **각각에 대한 Claude의 제안**

**대표가 동의/수정 → Claude가 수정된 행을 컬럼별로 제시 → 대표가 엑셀에 직접 반영**

### 문서 작성 규칙 (중요)
- **`비고` 칼럼 = 사양만.** "A에서 B로 바꿨다" 같은 변경 이력을 적지 않는다. 히스토리는 git이 담당한다.
- **`고민되는 점` 칼럼 = 질문 `(이어서)` 결론.** 원문서의 기존 규칙이며 판단 근거는 여기에 쌓는다.
- **예외**: `[2차]` 같은 범위 결정은 개발자가 지금 알아야 할 지시이므로 `비고`에 남긴다.
- 결정할 게 없는 행은 "넘어가도 됩니다"라고 표시한다.

### ⚠️ 코드 분석에 대한 지시 (2026-09-12 추가)
- **기존 앱 코드는 분석하지 않는다.** 기능 정의에 집중한다. **스키마(`schema.prisma`)는 참고해도 좋다.**
- 이유: 코드 수정 사항이 이미 너무 많아 기존 코드를 기준으로 삼는 것이 시간 낭비다.

### ⚠️ 스키마 접근 방침 (2026-09-12 결정)
- **기존 스키마의 구조는 가져간다.** 버리지 않는다.
  - 근거 ①: 감사 결과 스키마가 저장소에서 가장 멀쩡한 부분이다.
  - 근거 ②: 건물 → 유닛 → 계약 → 청구 → 수납 골격은 상업용에서도 동일하다.
  - 근거 ③: **마이그레이션 이력이 없다**(`pnpm migrate` = `db push`). 스키마를 고치는 것과 새로 쓰는 것이 기계적으로 같은 작업이라, "수정이 많다"는 부담이 실제 비용으로 이어지지 않는다.
- **단, 결과물은 새로 쓴다.** 72행 검토가 끝난 뒤 패치를 하나씩 적용하지 않고 **`schema.prisma` 전문을 한 벌 새로 작성**한다. 기존 구조와 `스키마정의서`를 펼쳐놓고 쓰므로 빠지는 것이 없다.
- 따라서 **아래 7장(누적 스키마 변경)은 대표가 읽고 판단할 표가 아니다.** 최종 설계 시 Claude가 쓸 재료 메모일 뿐이다.
- **운영 데이터는 없다** (2026-09-12 확인). 스키마를 어떻게 바꾸든 데이터 이전 비용이 발생하지 않는다.

## 4. 전역 결정 (모든 행에 적용)

| # | 결정 | 근거 |
|---|---|---|
| **G-1** | **차량번호를 시스템에서 관리하지 않는다** | 변경이 잦아 관리 실익 없음. `LeaseVehicle` 테이블 삭제. 주차면은 `ParkingSpace`에 **배정계약ID**를 직접 연결하는 구조로 대체 |
| **G-2** | **용어는 `임차인`으로 통일** | `입주자`/`임차사` 사용 금지. 임차인에 법인뿐 아니라 **개인사업자**도 포함되기 때문 (작은 건물의 경우) |
| **G-3** | **가전·가구 관리 기능 삭제** | 상업용 임대는 가전·가구를 제공하지 않음. `ApplianceFurniture` 계열 4개 테이블 삭제 |
| **G-4** | **관리자 권한 세분화는 2차 보류** | 초기 오픈은 슈퍼관리자 단독 사용 전제. "일반 관리자는 본인 담당 건물만" 류의 규칙은 매니저를 실제 운용할 때 구현 |
| **G-5** | **건물구분 선택지** | 오피스빌딩 / 근린생활시설(상가) / 지식산업센터 / 복합상가 / 물류창고 / 기타 |
| **G-6** | **유닛상태는 `공실 / 사용중 / 비운영중` 3종** | 상업용은 계약 체결 후 임차인이 직접 인테리어를 하므로 "공사중"이 불필요하고, "예약중"도 계약 상태로 판별 가능. `예약중`·`공사중` 삭제 |
| **G-7** | **계약 개시 기준 = 보증금 전액 입금** | 현장에서 계약금은 자리만 잡아두는 약속이고, 보증금이 들어오는 날이 실질적인 계약 시작일이다. 계약서 날인이나 계약 시작일 도래는 기준이 아니다 |
| **G-8** | **임차인 = 사업자 (법인 / 개인사업자)** | 사업자등록번호로 식별한다. **주민등록번호는 수집하지 않는다.** 계약 대표자와 실무 담당자가 대부분 다르므로 **담당자 정보를 별도로 받는다** |
| **G-9** | **계약시작일과 청구 기산일을 분리한다** | 계약시작일은 계약 기간·유닛상태·공실률의 기준. 임대료·관리비는 각각 기산일을 가지며 계약시작일보다 앞설 수도(소급) 뒤설 수도(렌트프리) 있다. 이 구조로 렌트프리가 표현되므로 **렌트프리를 별도 항목으로 두지 않는다** |
| **G-10** | **청구 항목은 고정액과 변동으로 나눈다** | 임대료·고정관리비만 계약에서 약정액으로 확정한다. 전기·수도·가스·주차 등 사용량에 따라 달라지는 항목은 계약에서 적용 여부만 정하고, 금액은 **건물 관리비 정산(PAY-8)**에서 산출한다 |

```

파기됨: 분쟁, 위반 등의 이유로 계약이 강제 종료되거나 무효 처리된 상태

 임대료와 관리비의 청구 시작일(기산일)은 계약시작일과 별개로 관리하며,

 보증금은 부가세 표기 대상이 아니다.

-기산일이 계약시작일과 다른 경우에만 해당 금액 옆에 기산일을 병기한다.
(예: 임대료 700만원 (2025.08.01부터))
```

```
달라 합산하면 판단이 어렵다.
```

```
-변동 항목은 매월 금액이 0원일 수 있다. (예: 무상 주차 3대 중 2대만 사용)
 0원인 항목은 청구 내역서에서 생략한다.

-주차요금은 계약에 배정된 주차면 수에서 무상 주차 대수를 뺀 초과분에만 부과한다.
 초과 대수 = max(0, 배정 주차면 수 − 무상 주차 대수). 주차면 배정은 PRO-3에서 관리한다.

-임대조건 조정 일정은 계약서에 "0000년 00월 00일부터 임대료 000원"과 같이 조정 일정이
 명시된 경우에 입력한다. 적용일 30일 전과 당일에 알림을 보내고, 계약 상세에서
 "조정 적용하기"를 눌러야 청구 금액이 갱신된다. 자동으로 갱신하지 않는다.

-동일 유닛에 진행중 계약이 이미 있으면 등록을 차단한다. 준비중 계약끼리 기간이 겹치는 것은
 허용하되 경고를 표시한다.

-계약이 미완인 경우를 대비하여 마지막 저장 버튼을 클릭할 때 두 가지 선택을 준다.
 "저장 (웰컴 메시지 전송 안함)", "저장 및 웰컴 메시지 전송"
-웰컴 메시지 전송 여부와 무관하게 임차인 계정의 비밀번호를 변경해서는 안 된다.
 기존 임차인이 추가 계약을 맺을 때 기존 계정이 잠기지 않아야 한다.

-[2차] 가상계좌 발급은 PG사 선정 후 구현한다. (PAY-5 참조)
-[2차] 알림 선호 채널(알림톡/이메일/둘다/수신거부) 설정은 NTF 계열 정비 시 함께 구현한다.
 단 청구서 이메일 발송은 초기 오픈 범위에 포함한다.

-반려동물, 외국인, 차량 정보는 사용하지 않는다.
 (상업용 임대는 해당 없음 / 차량은 관리 실익이 없어 주차면 배정으로 대체)
```

**【고민되는 점】**
```
-임대 청구 스케줄 생성시, 자동 알림 기능을 선택하게 할 것인지 아니면 기본 세팅으로 둘 것인지 고민

-자료 업로드를 00GB 까지 허용해야 할지 고민.

-계약상태중(준비중)인 상태에서 계약 시작일이 도래하면 시스템에서 자동으로 상태를 변경해야
할지 아니면 수동으로 변경할 때까지 기다려야 할지 고민.
(이어서) 시스템이 자동으로 계약 상태를 변경하도록 하고, 관리자가 이를 인식할 수 있도록 하는
것이 좋음.
(이어서) 예를 들어 보증금을 아직 내지 않았는데 시스템이 자동으로 계약 상태를 변경하면
웰컴 이메일/카톡 알림이 자동으로 발생되니 문제임. 아무래도 수동으로 하는게 좋을 것 같음.
(이어서) 자동 계약 상태 변경과 알림 전송을 따로 처리해야 함.
(이어서) 진행중 전환 기준을 보증금 전액 입금으로 정했으므로 수동 전환으로 확정한다.
계약 시작일 도래는 전환 사유가 아니다.

-가상 계좌 생성은 PG사에서 자동으로 가상계좌번호를 발급해 주지 않나? 개발사와 확인 필요
(이어서) 개발사 계약 종료로 확인 불가. PG사 선정과 함께 PAY-5에서 재결정하며 초기 오픈
범위에서 제외한다.

-포털에서 선호 알림 채널을 선택할 수 있어야 할 것 같은데, 그렇다면 알림 수신 거부를 할 수
있나? 한다면 모든 알림을 받지 못하게 되는 것인데, 경고 문구가 필요할 것 같음.
(이어서) 임차인 포털이 2차이므로 알림 채널 설정도 NTF 계열과 함께 2차로 미룬다.

-임차인을 개인으로 볼지 사업자로 볼지?
(이어서) 사업자로 본다. 상업용 임차인은 법인 또는 개인사업자이며 사업자등록번호로 식별한다.
주민등록번호는 수집하지 않는다. 계약 대표자와 실무 담당자가 대부분 다르므로 담당자 정보를
별도로 받는다.

-계약 등록 시 모든 청구 금액을 확정해야 하는가?
(이어서) 아니다. 임대료와 고정관리비만 약정액으로 확정하고, 전기·수도 등 사용량에 따라
달라지는 항목은 적용 여부만 정한다. 금액은 매월 건물 관리비 정산에서 산출한다.

-계약 기간 중 임대료 인상을 어떻게 관리하는가?
(이어서) 큰 회사는 5년 계약을 맺으면서 계약서에 인상 일정과 금액을 미리 명시하는 경우가
많다. 계약 등록 시 해당 일정을 모두 입력해두고, 적용일이 다가오면 알림으로 안내한 뒤
관리자가 확인하고 적용한다. 임차인과 협의해 조정을 유예하는 경우가 있으므로 자동 적용하지
않는다.
```

### PAY-8 · 건물 관리비 정산 *(신규 행)*

> ⚠️ 엑셀 12행과 14행이 **둘 다 `PAY-3`** 입니다. PAY 계열 번호 정리가 필요합니다.
> 아래는 기존 최대 번호(PAY-7) 다음인 `PAY-8`로 붙였습니다.

**【기능(분류:대)】** 청구/수납 관리 · **【기능(분류:중)】** 건물 관리비 정산
**【설명】** 건물 단위로 공과금 고지서와 유닛별 검침값을 입력해 유닛별 청구 금액을 산출한다.
**【대상 사용자】** 슈퍼관리자, 관리자 · **【주요 액션】** 생성, 조회, 수정 · **【우선순위】** 매우 높음

**【입출력 데이터】**
```
필터: 건물고유이름, 정산회차(년월)

(고지서 입력)
[목록] 청구항목, 고지서 총사용량, 고지서 총금액(부가세 포함)
[전기 추가 입력] 공급가액, 부가세, 전력기금, TV수신료

(검침 입력)
[목록] 유닛고유번호, 청구항목, 검침일, 전월 검침값, 당월 검침값, 사용량(자동계산)
[입력시] 검침일, 당월 검침값
※ 검침 기록은 원본이며 수정하지 않는다.

(조정)
[목록] 유닛고유번호, 청구항목, 원본 사용량, 조정 배수, 정산 사용량, 사유, 작성자, 작성일시
[입력시] 조정 배수, 사유

(산출 결과)
[목록] 유닛고유번호, 임차인, 청구항목, 검침 사용량, 잔여 배분 사용량, 정산 사용량, 청구금액
합계 검증: 청구항목별 (유닛 청구금액 합계 = 고지서 총금액) 일치 여부 표시

(정산 확정)
정산 확정 → 계약별 청구서 생성
```

**【비고】**
```
-임대료와 고정관리비는 계약 약정액이므로 이 화면에서 다루지 않는다. 사용량에 따라 금액이
 달라지는 항목만 정산한다.

-산정 규칙은 모든 항목에 동일하게 적용한다.
 1) 유닛 검침 사용량 = 당월 검침값 − 전월 검침값
 2) 정산 사용량 = 검침 사용량 × 조정 배수
 3) 잔여 사용량 = 고지서 총사용량 − Σ 정산 사용량
    (검침분을 임차인이 직접 납부하는 건물은 고지서가 이미 공용분이므로 잔여 = 총사용량)
 4) 가중치 = 배분 기준값(정산 사용량 또는 임대면적) × 조정 배수
 5) 잔여 배분 = 잔여 사용량 × (가중치 ÷ Σ가중치)   ※ 부담 대상 유닛에만
 6) 유닛 정산 사용량 합계 = 정산 사용량(청구하는 경우) + 잔여 배분
 7) 유닛 청구금액 = 고지서 총금액 × (유닛 정산 사용량 합계 ÷ 고지서 총사용량)
 8) 전력기금과 TV수신료도 같은 비율로 환산한다.

-검침 기록은 원본이며 수정하지 않는다. 보정이 필요하면 조정 배수를 별도 기록으로 남기고,
 사유와 작성자를 함께 저장한다. 조정은 해제할 수 있으며 회차별로 이력이 쌓인다.
-조정 배수의 기본값은 유닛에 설정된 기본 조정 배수(PRO-4)이며, 해당 회차에만 다르게 줄 수 있다.

-정산 확정 전까지 고지서 금액이나 검침값을 수정하면 전체가 재계산된다.
-확정 시 청구항목별로 유닛 청구금액 합계와 고지서 총금액이 일치하는지 검증하고, 일치하지
 않으면 확정할 수 없다.

-격월 또는 연 1~2회 발생하는 항목은 해당 회차에서 항목을 추가해 정산한다. 청구 주기를
 미리 고정하지 않는다.
-주차요금 중 방문 차량 요금은 경비원이 현장에서 계산한 결과를 유닛별 월 합계 금액으로
 입력한다. [2차] 입·출차 시간 기록과 시간제 자동 계산은 주차 관제 연동 시 검토한다.

-[2차] 세금계산서·계산서 발행과 은행 입금 확인은 초기 오픈 범위에서 제외한다.
 청구 내역서를 임차인 담당자 이메일로 발송하는 것까지가 초기 오픈 범위다.
```

**【고민되는 점】**
```
-공용 사용량을 배분할 때 특정 유닛에 배수를 적용하면 총액이 고지서와 어긋나지 않는가?
(이어서) 배수를 먼저 반영해 비율을 잡는다. 배분한 다음에 배수를 곱하면 합계가 고지서를
초과하게 되어 실제 낸 금액보다 더 걷게 된다. 배수를 먼저 반영하면 한 유닛이 더 내는 만큼
다른 유닛이 덜 내고 총액은 항상 고지서와 일치한다.

-계량기가 고장나거나 모델이 달라 사용량이 실제와 다를 때 검침값을 고쳐야 하는가?
(이어서) 고치지 않는다. 검침값과 사용량은 원본이므로 그대로 보관하고, 조정을 별도 기록으로
남긴다. 원본이 남아 있어야 나중에 금액 산출 근거를 추적할 수 있고 조정을 되돌릴 수 있다.

-조정 배수를 공용 배분에만 적용할지, 전용부 청구액까지 적용할지?
(이어서) 전용부와 공용 배분 모두에 적용한다. 조정의 의미를 "이 유닛의 사용량을 이만큼으로
본다" 한 가지로 통일하면 배수를 하나만 두어도 되고 총액도 항상 맞는다.

-검침기가 일부 유닛에만 있는 건물은 어떻게 배분하는가?
(이어서) 검침 가능한 유닛부터 사용량을 확정하고, 남은 사용량을 검침기 없는 유닛에 임대면적
비율로 안분한다. 검침기가 모두 갖춰진 건물은 남은 사용량이 순수 공용분이므로 전체 유닛에
검침 사용량 비율로 안분한다.
```
